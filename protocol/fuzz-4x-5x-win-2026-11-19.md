# Packet fuzz of the Windows 4.x and 5.x clients (2026-11-19)

Status: in progress. This file is updated as each build finishes.

The 4.20r8 and 5.24r4 server-to-client probe set (`wine-core`, `widths`, `widths-fix`, `bytes2x`,
`baddytypes`, `loadgani3w`) is run on every other Windows 4.x and 5.x build we hold. Each row in
[`probe-results.tsv`](probe-results.tsv) repeats the reference row's packet and payload. Its observed
column keeps the reference text when the result matches, and starts with `DIFFERS` when it doesn't.

## How it ran

- The 5.x builds ran natively in the Win10 lab VM, not under Wine. The Debian probe VM had been at
  load 7–9 for hours, and the load guard below would have held every run.
- The host ran a seihai-gserver world with its 4.x–6.x login lobby. `gen5probe.py` sat in front of the
  world port, and the lobby sent clients on to the proxy. Screenshots came from the VM's frame
  buffer.
- The canary box (the HUD bomb count) is found automatically: it is where the `ref-01` and `ref-99`
  shots differ. Every shot in both builds fell clearly on one side (no unclear shots).
- The Win10 VM is shared. Runs took turns through a desktop lock in slices of 18 minutes at most.
  While a run held the lock, its login and world ports were set in the guest, and both were put back
  when it released.
- `tools/probe/lab/loadguard.sh` is the wait-while-busy wrapper for the shared Linux VM. It waits
  while the 1-minute load is above `LOADMAX` (default 4), polls every 30 s, and logs each hold.
  `runwine.sh` now also knows the new builds (403, 404, 411, 500, 530, 531), takes `PROBE_ROOT`,
  `DISP` and `CLFT`, and gives the 4.0x stubs a prefix with Direct3D `csmt` = 0.

## Results so far

| Build | Canary cases | Differ from reference | Client gone | Notes |
|---|---|---|---|---|
| 5.00r7 | 130 | 0 | 0 | |
| 5.24r3 | 130 | 0 | 0 | |

| 5.31r4 | 130 | 0 | 0 | baddy types: see below |

The 130 canary cases are `wine-core` (32), `widths` (82), `widths-fix` (9) and `bytes2x` (7). The first
three are compared with 5.24r4, and `bytes2x` with 4.20r8 (5.24r4 has no `bytes2x` run).

**5.00r7, 5.24r3, 5.30r3 and 5.31r4 parse player props exactly like 5.24r4.** All four builds lose the canary in the same 7 cases as 5.24r4 (`p77-i5`, `p83-i5`, `p90-i3`, `id51`, `id76`, `id77`, `id83`). So 5.00r7 already reads 82 as a string, which 4.20r8 does not. In detail:

- every documented width holds;
- 77 and 83 are skipped as one byte;
- 82 is read as a string;
- an unknown own id is skipped as one byte;
- the unknown PLO ids are ignored;
- NUL, `ff`, `80` and `1f` bytes inside a message are harmless.

### Clock gate

The packed 5.3x clients run only with the clock on or after their link date, and not much later:

- 5.31r4 at 2010-10-15 (before its link date) logs in. It then dies with a fail-fast (BEX `c0000409`
  in KERNELBASE) within seconds of the first new baddy.
- At 2012-11-20 it exits silently right after printing its beta banner.
- At 2011-01-20 it plays.

### Baddy types on native Win10

The client window closes 3–80 s after injected baddies become active. The types it happens at are
scattered: 24, 30, 33, 34, 38, 44–48, 50 and 56–58, out of 0–60, 100, 150, 200 and 223. Type 21
crashed twice in a row and then passed.

The 5.24r4 reference build, run natively on the same setup, drops the same way (27, 28, 30, 31, 33,
34, 37 and 38 in a partial sweep). Under Wine, 4.20r8 never dropped. So this comes from the native
Win10 setup and its baddy handling: the client leads the baddies and asks for sounds such as
`crush.wav` that the lab world doesn't have. It isn't a 5.3x parse difference.

The `baddytypes` row for 5.31r4 records this as an environment note. Telling the cause apart needs
the same sweep with the baddy sounds present.
