# Packet fuzz of the Windows 4.x and 5.x clients (2026-11-19)

The 4.20r8 and 5.24r4 server-to-client probe set was run on every other Windows 4.x and 5.x build we
hold: `wine-core`, `widths`, `widths-fix`, `bytes2x`, `baddytypes` and `loadgani3w`. 4.20r8, 5.12 and
5.24r4 were already covered (2026-11-18). **[lab]**

Each row in [`probe-results.tsv`](probe-results.tsv) repeats the reference row's packet and payload. The
observed column keeps the reference text when the result matches, and would start with `DIFFERS` when it
doesn't. No row here starts with `DIFFERS`.

The 130 canary cases are `wine-core` (32), `widths` (82), `widths-fix` (9) and `bytes2x` (7). `bytes2x`
is always compared with 4.20r8, because 5.24r4 has no `bytes2x` run.

**Player props.** 4.03r3–4.11 read them like 4.20r8, and 5.00r7–5.31r4 like 5.24r4:

- Every documented width holds.
- An id with no case is skipped as one byte. The canary is lost in the same cases as in the
  reference:
  - **4.x:** 77, 82, 83 and 90 with the longer value. 4.03r3–4.11 have no case for 82, like 4.20r8.
  - **5.x:** 77, 83, 90, 51 and 76. 5.00r7 already reads 82 as a string, like 5.24r4.
- Unknown PLO ids (60, 78, 81, 83, 110) are ignored.
- NUL, `ff`, `80` and `1f` bytes inside a message are harmless in every build.

So prop 82 became a string between 4.20r8 and 5.00r7. Nothing else in this set changed from 4.03r3 to
5.31r4.

### PLO_LOADGANI (195)

For this run the lab world was given the reference world's ganis, and the plan's M2 line was fixed. That
line had a quoting error (`t:\""`) that `shlex` rejects, which stopped every run at M2. The 2026-11-18
reference had used a pre-expanded copy.

- Every section gives the same gani outcome as 5.24r4 (`lgw524`), except one.
- **After M4** (`NUL ff 80` inside the `SETBACKTO` name), `hurt` falls back to a gani named `00 ff 80`.
  The NUL does not end the name. This happens:
  - in all seven builds, both natively and under Wine;
  - in a native 5.24r4 control run (`c524n`).
- Only the 2026-11-18 Wine run of 5.24r4 showed no fallback. Its "NUL ends the name" reading looks
  specific to that one run.
- The 4.20r8 reference run (`lgw420`) can't be compared, because that account rode a horse the whole
  time (`ridestill`).

## Method

- **5.x: the Win10 lab VM, native.**
  - The host ran a seihai-gserver world with its 4.x–6.x login lobby. `gen5probe.py` sat in front of the
    world port.
  - The VM is shared, so runs took a desktop lock in slices of 18 minutes or less.
  - While a run held the lock, the guest's login and world ports pointed at this stack. Both were put back
    when the lock was released.
  - Screenshots came from the VM's frame buffer.
- **4.x: the Debian lab VM under Wine,** with `tools/probe/lab/runwine.sh 403|404|411`.
  - Each run had its own network namespace, Wine prefix (Direct3D `csmt` = 0) and display.
  - The servers were the gs2emu GS1 Lab world, with the extra login tokens allowed.
- **Canary: the HUD bomb count.**
  - On Win10, the box is found where the `ref-01` and `ref-99` shots differ.
  - Under Wine, the grass animation also changes between those two shots, so the box was fixed on the
    digits.
  - No shot was unclear.
- **`tools/probe/lab/loadguard.sh`** waits while the shared VM is busy.
  - By default it waits while the 1-minute load is above `LOADMAX` (4).
  - With `MEMMIN_MB=N` it waits while `MemAvailable` is below N MB instead, and only logs the load.
  - The VM's 2 vCPUs sat at load 6–20 for hours, so the 4.x runs used `MEMMIN_MB=800` at `nice -n 10`,
    with the load logged every 30 s.
- **`runwine.sh`** now knows clients 403, 404, 411, 500, 530 and 531, and takes `PROBE_ROOT`, `DISP` and
  `CLFT` (faketime).

No server or client bug turned up that needs an issue. Two points matter for emulation:

- A NUL inside a `SETBACKTO` name is kept as part of the name.
- Prop 82 is read as a string from 5.00r7 on.
