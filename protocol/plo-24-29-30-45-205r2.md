# PLO 24, 29, 30 and 45 in 2.05 rev 2

Date: 2026-11-12. Tags: **[bin]** static read of the Windows `Graal v2.05 rev2.exe` export (the same pass the other 2.05r2 notes use). Only plain behaviour is given here, with no addresses. Nothing was run.

The manual listed these four server-to-client messages as `unmeasured` for both the layout and the client action. All four are cases in 2.05r2's main receive switch, and they are read here. Ids 55 and 56 (`PLO_ADDPLAYER` / `PLO_DELPLAYER`) are not in that switch, which agrees with the `·` in `packet-ids.md`.

## 24 `PLO_NPCMOVED`

Layout: `i3 npc id` (three GCHAR-style bytes, `(b0−32)·16384 + (b1−32)·128 + (b2−32)`), `c x·2`, `c y·2`, then `rest` = image name.

1. Bodies shorter than 3 bytes are ignored.
2. The NPC is looked up by id in the client's NPC list. An unknown id is ignored.
3. X and Y are read as half-tile values (byte − 32, divided by 2).
4. The image name is normalised the same way other file names are. The handler compares it with the NPC's current image name. In the export, the "names are equal" exit leans on a flag the decompiler tracks badly, so whether a matching name skips the rest is **not tagged**.
5. Otherwise the client:
   - clears the NPC's cached sub-objects;
   - **removes the NPC from the NPC list of every loaded level**;
   - with an image name under 3 characters, leaves the NPC with no image; with a longer one, loads that image and sets the NPC's X and Y from the message.

So 24 detaches a server-side NPC from the levels the client holds and re-images it. That fits the server-source reading that the server sends it when an NPC leaves the player's level. The level-move meaning itself is **[srv][inf]**.

## 29 `PLO_NPCDEL`

Layout: `i3 npc id`. Nothing follows that the client reads.

1. Bodies shorter than 3 bytes are ignored.
2. The NPC is looked up by id. An unknown id is ignored.
3. The shared NPC-removal routine runs. It:
   - takes the NPC out of the global NPC list and out of every loaded level's NPC list;
   - drops the level-board links that point at it;
   - clears the player's carried-NPC slot if it held this NPC, and resets the carry pose;
   - removes its entry from the list behind the on-screen NPC chooser, and clamps that list's selection;
   - clears any player that pointed at it.
4. The NPC object is freed.

## 30 `PLO_FILESENDFAILED`

Layout: `rest` = file name.

1. An empty body is ignored.
2. The name is normalised. Text from a fixed separator onwards is cut off by the same helper the other file messages use.
3. The client creates an **empty, zero-length in-memory file** with that name.
4. It runs the shared request-list release (→ §2.7): the name leaves both request lists, the next waiting name goes out if one was among the first four, and the name joins the settled list.
5. It passes the empty file to the normal "file received" routine. That routine also handles `.gani` names, so a failed `.gani` is installed as an empty animation rather than staying missing.

This answers the open line in `client-internals/decomp-findings-2026-10-25-e/01-request-lists.md`: beyond not asking again, the client also treats a failed file as **received and empty**.

## 45 `PLO_FILEUPTODATE`

Layout: `rest` = file name.

1. An empty body is ignored.
2. The name is normalised the same way as for 30.
3. Only the shared request-list release runs. No file object is created.

The difference between 30 and 45 in 2.05r2 is therefore one step: 30 hands an empty file to the "file received" routine, and 45 does not. Only that routine's `.gani` branch was read. What it does with an empty file of another type (an image, a level) is not traced.
