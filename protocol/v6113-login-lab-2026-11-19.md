## What this run does and does not establish

- **Does:** the stock-client trust-anchor swap described as "the only lab path" in the method
  note does **not** work as an in-memory modulus patch (below). The clean-room login
  handshake runs end to end on loopback, and the first-hop **token structure** of the
  clean-room path is defined.
- **Does not:** it does **not** establish the authentic 6.1.1.3 client's first-hop login/list
  path, and it does **not** establish any post-login Login/play reply contract for 6.1.1.3 or
  a 6.1.1.3-vs-6.037 reply difference. Both runs stop at or before the post-login exchange.
  Those stay open and must be sourced from the existing capture/status notes with their own
  evidence tags, not from this run. **[lab][inf]**

## 1. The stock-client trust-anchor swap does not flip the verdict **[lab]**

The method note's plan for driving a *stock* 6.1.1.3 client was to replace the compiled-in
connector trust anchor — serve a lab `conf.gs` signed with a lab key and make the client
verify against a lab public key swapped into its memory once Themida had unpacked it.

A loopback attempt at that swap came back a **decisive negative**. The packer virtualizes the
signature check and consumes the public modulus inline during verification, so swapping the
materialized modulus in host memory at verify time does **not** change the client's accept/
reject verdict: a lab-signed reply is still rejected. The earlier wording in
`v6113-status.md` (open item 3) — "an in-memory at-verify-time patch, not a static offset" —
was still too optimistic: the in-memory patch itself is defeated by the virtualized verify.

So the stock-client lab path is not an anchor swap. What remains for a stock client is
replaying a **genuine** signed `conf.gs` (which a lab cannot forge, and whose decrypted
post-287 stream a lab still cannot read without the operator private key), exactly the limits
set out in [`connector-script.md`](connector-script.md) §4. The faithful stand-in for lab
work stays the clean-room `graal-client-repro`, which bakes in its **own** key and runs its
**own** signed script. **[lab][inf]**

## 2. The clean-room login runs; its first-hop token structure is defined **[lab]**

A loopback exercise of the Seihai clean-room secure login (`SEI00001`, our own protocol) with
the 6.1.1.3 clean-room client against a lab gserver completed the key exchange and the sealed
login handshake. In that clean-room path:

- The client places the literal `SEI00001` marker in the version-token slot.
- The build's own version token is carried as an **inner token** inside the first client
  message, and the server reads that inner token and proceeds as that build.

This is a fully-defined clean-room path. It is **distinct** from the authentic 6.1.1.3 first
hop, which is **not** settled here (see below). The run does not enter the post-login
exchange, so it says nothing about Login/play replies. **[lab]**

## 3. Server-side version-catalogue gap **[lab][srv]**

The faithful 6.1.1.3 token `GNP1905C` is not yet in the server-side version catalogue
(`gs2lib`), so a faithful-token login cannot be accepted server-side as it stands; the clean-
room run used a known stand-in token so the lab server would accept the build. This is a
catalogue gap, not a protocol problem, and it is why a Gen5 `G3D0311C` (6.037) stand-in is
sometimes used in its place — see the token contrast in
[`v6-login-token-explained.md`](v6-login-token-explained.md) and
[`v6037-hello-diff.md`](v6037-hello-diff.md). `GNP1905C` reaches the wire only from the
connector script's `sendRaw`, never from a compiled-in client string.

## Still open after this run (carried, not closed)

- **The authentic 6.1.1.3 first-hop login/list path.** Structurally, the authentic image
  carries no compiled-in version token and no id-5 login constructor of the 6.0x shape; the
  token is a `sendRaw` literal inside the server-supplied connector script (unlike 6.0.3.7,
  which stores and decodes its own token for the id-5 login). So the token arrives from the
  connector — but **which path it takes on the first login/list hop is still the open
  question**, to be sourced from the capture/status notes, not from this run.
  (`v6113-login-lab-method.md`.) **[lab]**
- **The post-RC4 login packet and the 6.1.1.3-vs-6.037 Login/play reply difference.** Not
  established here. `v6037-hello-diff.md` compares the two builds at login/framing/property
  level, not as a required-reply list; the 6.1.1.3 reply contract is partly capture-derived
  (owner-held `[cap]`) and partly open (`v6113-status.md`). **[lab]**
- **A full end-to-end logged-in session of the *real* client**, with both gates wired as one
  chain. The anchor-swap route is now ruled out for a stock client (item 1), so this needs a
  genuine signed reply, which stays owner-held and off-git. **[lab][inf]**
