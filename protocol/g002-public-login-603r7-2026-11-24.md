# Public Login: Windows 6.03r7 guest on port 14900 (2026-11-24)

Derived note. One owner-approved classic Login check (Asia/Tokyo afternoon) against `<login-host>` on port **14900**. Manual pace, one session at a time, no token sweep, no game warp, no listserver follow-on. Login-frame bytes, credentials, machine hashes and the host name stay private. Partial close of matrix unknown #3 / App. E#3 / gap **G002**: what today's public Login sends to a stock **6.03r7** token.

## Login sent

One plain zlib frame (no cipher, no compression type byte), matching the Windows 5.x/6.x guest shape in [`v5v6-windows-unpacked.md`](v5v6-windows-unpacked.md):

- `GCHAR 5` (client type) + `GCHAR` key + token **`G3D0311C`** (Windows 6.03r7)
- account kind **guest** (documented guest password; not printed here)
- trailer `win` + empty quoted machine-id placeholders + quoted OS string
- trailing LF

No language packet and no `basepackage.gupd` request on the session that produced the finding below.

## Result

| step | outcome |
|---|---|
| TCP connect to **14900** | accepted |
| S→C after login | **one** uncompressed gen-5 frame (ctype 2), 35 bytes on the wire |
| ids | **25** `PLO_SIGNATURE`, then **16** `PLO_DISCMESSAGE` |
| disc text | `Please update your version..` |
| 190 / package / level / weapon burst | **absent** |

So the public classic Login path still answers a gen-5 `G3D0311C` guest login, but it does **not** enter the GUI-script lobby for that token: no S→C **190**, no `basepackage.gupd` traffic, no backdrop level. The server stops the session with a disconnect message that asks for a newer client.

A second session that sent language + one `WANTFILE basepackage.gupd` after the same login hit a connection reset; that run was stopped immediately and is not treated as a second finding.

## What this settles

- Official Login on **14900** is reachable and speaks gen-5 to Windows **6.03r7**.
- For `G3D0311C`, the first S→C content is the version-reject pair **25 + 16**, not the lobby burst described in [`login-session-known.md`](login-session-known.md) / observed on a community Login in [`login-session-observed.md`](login-session-observed.md).
- The E#3 best guess (lobby from `basepackage.gupd` + S→C 190) remains the right model for a Login that **accepts** the client; it is simply not what today's official Login sends to 6.03r7.
