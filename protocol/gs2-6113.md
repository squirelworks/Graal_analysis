# GS2 in Windows 6.1.1.3: nothing new is visible

Date: 2026-11-07. Static read. Nothing was run. Tags: **[bin]** the 6.113 listing and the unpacked 6.00 reading already on main · **[doc]** the MPL-2.0 Preagonal compiler, cited by file and line, not pasted.

The container, the opcode names and the load path for 4.2.0.8, 5.0.0.7 and unpacked 6.00 are `protocol/gs2-client-vm.md`. The effect of each client-only opcode is `protocol/gs2-client-only-opcodes.md`. This page is only the 6.113 delta.

## What 6.113 cannot show

The listing has no script container, no load path, no opcode switch, no peephole, and no builtin table. There is no `GRESCR01`, no `.code`, no `setScript`, and no `TGraalVar`. A search finds none of the segment markers as a parser and none of the fold opcodes as a dispatcher. **[bin]** (`client-internals/engine-6113.md#subsystem-map`)

Export ordinals on the `QPlay.exe` directory are not GS2 opcodes. Ordinal 121 in that directory is `Md5Update`. Ordinal 54 is not even one of the annotated cipher exports. **[bin]** (`client-internals/engine-6113.md#the-export-surface`)

So 6.113 adds no opcode, no superinstruction and no builtin. It also cannot show a removal. In particular it cannot show whether cases 48 and 49, present in 5.0.0.7 and absent in unpacked 6.00, came back, or whether any fold past 242 exists. **[bin]**

## What unpacked 6.00 already has

Read from unpacked Windows 6.00r2 and 6.00r4, not from this stub. 6.00r4's cases match 6.00r2. **[bin]** (`protocol/gs2-client-vm.md#5007-and-unpacked-600`)

The container is still four big-endian segments, types 1–4, markers `F0`–`F6`, and a decoded instruction of 24 bytes. The compiler writes that shape and then a trailing newline (`GS2Compiler.cs` `ToArray`, lines 1855–1873). The client walk stops on any other type. The compiler's default `0xAC` wrapper is not a segment stream; `setScript` does not run a file that starts with it. **[bin]** (`protocol/gs2-client-vm.md#same-container`) **[doc]** (`npc-library/preagonal-gs2.md#pipeline`)

Weapons and classes still go through `GRESCR01` on a `.code` file of at least eight bytes. That magic is in the 6.00 images and not in the 6.113 listing. **[bin]** (`protocol/gs2-client-vm.md#script-cache`, `protocol/v6113-wire.md#file-transfer-and-the-script-cache`)

Against the 4.2.0.8 switch, 6.00 adds cases 54 and 121 and folds 234–242. It does not have cases 48 or 49. Those two are 5.0.0.7 only. Folds 200–233 are already in 4.2.0.8. The 6.00-only folds are pairs recognised after decode, so they never appear as bytes in the file:

54 builds a value with type tag 4 from the top of the stack. 121 adds the two numbers, unless either value is a string, in which case both go through the string helper. That is the 5.0.0.7 reading, and 6.00 matches it. **[bin]** (`protocol/gs2-client-vm.md#opcodes-added-after-4208`)

## Against the compiler

The compiler is [Preagonal.Scripting.GS2Compiler](https://github.com/Preagonal/Preagonal.Scripting.GS2Compiler) at `7878bc5`, SPDX MPL-2.0. Its private `Op` enum is `GS2Compiler.cs` lines 2160–2275. The companion engine's enum is `Opcode.cs` lines 3–126 in [Preagonal.Scripting.GS2Engine](https://github.com/Preagonal/Preagonal.Scripting.GS2Engine) at `f8b5f13`. The builtin-to-opcode map is `GS2Compiler.cs` lines 1612–1649. Anything else the compiler calls is opcode 6, by name. It does not emit a peephole. Opcodes 200 and above are not in its enum. **[doc]** (`protocol/gs2-client-vm.md#compiler-and-builtins`, `npc-library/preagonal-gs2.md`)

6.00, not 6.113, is the client side of the comparison.

In the client, not emitted by the compiler: 43, 45, 46, 47, 54, 66, 67, 104, 121, 190, the folds 200–233, and on 6.00 the further folds 234–242. Cases 48 and 49 are in 5.0.0.7 and not in 6.00. The compiler's enum has no member for any of these. **[bin][doc]** (`protocol/gs2-client-only-opcodes.md#which-image-dispatches-it`)

The other way: the client notes say 4.2.0.8, 5.0.0.7 and unpacked 6.00 accept every opcode the compiler emits. The compiler does emit bytes its own companion enum does not name (`waitfor` 11, inline conditional 44, bitwise xor 78, bitwise invert 79, shifts 101 and 102). That gap is inside the Preagonal pair. It is not a 6.113 finding, and 6.113 cannot show the Graal client dropping one of those bytes. **[bin][doc]** (`protocol/gs2-client-vm.md#what-differs`, `npc-library/preagonal-gs2.md#control-flow-and-the-opcodes-they-named`)

Named the other way around, same byte: client `loopcheck` (9) against compiler `CmdCall`; client `savestackpos` (10) against compiler `Jmp`; client `massassign` (51) against the compiler's end-of-parameters; client `beginswith` and `endson` (116, 117) against compiler `starts` and `ends`. Unchanged by 6.113, because 6.113 has no names. **[bin][doc]** (`protocol/gs2-client-vm.md#what-differs`)

Builtins follow the same split. The compiler turns `sleep`, `waitfor`, the math and string helpers, and the array methods into their own opcodes, and leaves game commands as opcode 6. Unpacked 6.00r4 registers `resolveHost`, a DNS lookup, which is not in that opcode map, so a source call of that name would be opcode 6. 6.00r2 has no such name. 6.113 has no builtin table and no `resolveHost` string, so it does not show the name being added or removed after 6.00r4. **[bin]** (`client-internals/engine-600r4.md#what-changed-in-two-weeks`) **[doc]** (`protocol/gs2-client-vm.md#builtins-the-compiler-turns-into-opcodes`)
