# Outgoing senders, unpacked 6.1.1.3 and 6.0.3.7

Static read of both listings. Nothing was run. [bin]

## Fixed ids

`sendraw` in 6.1.1.3 calls the connection send with id −1 and the caller's
bytes. That send appends those bytes and does not add a packet id of its
own. [bin] (`protocol/v6113-hello.md#the-eight-characters`)

`senddata` in 6.1.1.3 calls the same send. The id and the body are the two
arguments. No constant id is compiled into `senddata` itself.

Unpacked 6.0.3.7 has no plaintext `sendraw`, `senddata`, `setprotocol` or
`onSend` name. Its login constructor sends packet id 5, and the body of
that send is the upper-cased eight-character token `G3D0311C`.
[bin] (`protocol/v6113-hello.md#against-unpacked-6037`)

## The outgoing table

6.1.1.3 keeps 256 outgoing slots. `setoutdatahandlers` fills every slot
with the all-ones dword, then copies the script's list over the front of
the table and stops at 256. A negative slot means "do not send". Slot 254
means "raise the script event instead of sending". Any other value is the
packet id passed to the connection send. The image stores zeros in this
table; the fill above replaces those zeros when the script method runs.
The 256 values are not listed here.

Each name below is a real function. It loads one slot of that table. A
negative slot returns without sending. Slot 254 raises the script event of
the same name. Any other value is sent as the packet id, with a body the
function builds. Where a type string is pushed next to the script event, it
is the string in the table. The letters were not given a meaning beyond
what is written. Functions with no type string still raise the event; a
type string was not next to that call.

For `onSendBoardModify`, the numbered path (any slot other than 254) was
read far enough to see the send: the slot value is the packet id, and the
body is a string of bytes stored plus 32, including one byte stored plus
96. The same split was not repeated for the other 54 names.

Methods named `send` and `sendudp` are in the 6.1.1.3 image. No constant
packet id was recovered for either.

The `tclient_set*` methods are incoming handlers or script setters. They
are not senders of a compiled packet id, except where one of the events
above is the matching send (`onSendPlayerProperties`,
`onSendBaddyProperties`, and the other names in the table).
