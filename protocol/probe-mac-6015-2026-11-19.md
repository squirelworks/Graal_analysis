# Packet probe: 6.015 Mac (Lion VM)

Date: 2026-11-19

This brings the packet probe ([`probe-targets-2026-11-18.md`](probe-targets-2026-11-18.md),
[`probe-results.tsv`](probe-results.tsv)) to the **6.015 macOS client**, running in the Lion 10.7.5
research VM. It is the first Mac client driven through `gen5probe`. The x86_64 slice of the universal
6.015 build runs on Lion; the PowerPC Mac builds (3.153, 4.x, 5.12) need a Tiger/PPC environment and
are not covered here.

Lab only. Everything stays on loopback / a private QEMU user-net; nothing reaches a public server.
Raw captures stay off the repo.

## Method

The Lion lab VM (its research start script) already has the wiring: a QEMU user-mode NIC with
`restrict=on`, the guest `/etc/hosts` maps the official Graal login/list hosts to a fixed lab
address in the guest's private user-net, and `guestfwd` sends the guest's login port (14900) to the
host, which forwards it on to the lab VM that runs the server. So, unlike the Linux clients, no
`hostshim`/`DYLD` insert is
needed — the guest's hosts file is the redirect, and the client's own `license.graal` login host
resolves to the lab.

To keep the server stack **inside a VM** (not bare-metal on the host), the gserver + `gen5probe` run
in the `debian-lab446` lab VM; two runtime `hostfwd_add`s (via QMP) expose the debian proxy on the
host loopback ports the Lion `guestfwd` targets. The gserver is a single **normal playable world**
(not a serverside login that serverwarps), so the Mac logs in and plays over one gen5-probed
connection — avoiding a cross-VM serverwarp address. The Mac side is driven by `qmp.py`
(screenshot + keyboard into the guest's Terminal): copy `Graal.app` off the read-only `GRAALIN`
volume, `chmod +x`, and launch the x86_64 binary; it auto-connects as account `guest`.

The client's login decodes cleanly as **gen 5, token `G3D3107A`** (6.015 Mac), and the session is
stable (no reconnect loop, client alive through the whole plan). Canary is the screen-free
**chatback** (a clientside GS1 NPC reflects the player's bomb/gralat counts into chat, read from the
proxy `C>S` stream) — 6.x supports `setplayerprop #c`, as 6.03r7 does.

## Results

6.015 Mac ran the full core plan. It matches the **6.x profile** (the 6.03r7 pilot), and so differs
from the 4.x line exactly where the prop-width table changed between 4.x and 6.x:

| probe | 6.015 Mac | reading |
|---|:-:|---|
| prop 3 (3-byte `i3:`) | lands | 3-byte rupees |
| prop 77 | 5-byte lands, 1-byte loses | **read as 5 bytes** (4.x reads 1 byte) |
| prop 78 / 79 / 80 (2-byte `s:`) | land | 2-byte |
| prop 81 (1-byte) | lands | 1-byte |
| prop 82 (`str:`) | **lands** | string prop (4.x/3.04 desync here) |
| prop 83 | 5-byte lands, 1-byte loses | **5-byte gralat** (4.x reads 1 byte) |
| prop 90 | 1-byte lands, 3-byte loses | 1-byte |
| unknown PLO 60/78/81/83/110 | ignored, alive | no crash/desync |

So the native-client layering now reads, across OS and build:

- **6.x** (6.03r7 Linux, 6.015 Mac): prop 83 and 77 are the wide (5-byte) form; prop 82 is a string.
- **4.x** (4.03r1–4.20r8 Linux, 4.20r8 Windows): prop 83 and 77 are 1-byte; props 78–80 are 2-byte;
  prop 82 is not a string.
- **3.04** (Linux): as 4.x, except props 78–80 are not yet defined (1-byte skip).

Each generation is uniform across its builds and across OS; the differences are between generations,
at the points where the prop-width table was extended.
