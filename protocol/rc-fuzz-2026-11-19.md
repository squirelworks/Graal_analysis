# Fuzzing the 2004 Remote Control: no crash on the rc-core set

Date: 2026-11-19. Tags: **[lab]** one run in the probelab. Evidence id: `RC-FUZZ-20261119`.

First packet-fuzz of a Remote Control client. Malformed and out-of-range server→client packets
were injected into a live RC session through `tools/probe/gen5probe.py`, with the harness added in
the same change (`tools/probe/lab/runrc.sh`, `rc-core.plan`, `rccanary.py`). Lab only, loopback
only; the run was isolated in its own network namespace and display and touched no other lab.

## Setup

- RC: the 2004 Delphi `RemoteControl.exe`, window title `Graal Remote Control 2004/01/17`, token
  `GSERV024`. Under Wine, behind the proxy. It logged in **type 6, generation 5**, account `super`
  — confirming the proxy needs no decode change for the type-6 RCs (the token sits where a version
  string goes). **[lab]**
- Server: the lab GServer-v2 fork (`gs2emu-73`) and `seihai-listserver`, the world bound to a
  second loopback address behind the proxy on `14804`. The `super` account needed `ADMINRIGHTS`
  and an open `IPRANGE`, not just a place on the staff list, or the server replied
  `You do not have RC rights.` (now set by `runrc.sh`). **[lab]**
- Plan: `rc-core.plan` — oversized string lengths, prop-stream run-off, huge counts, NUL/high
  bytes, unknown and deprecated ids, an empty-body sweep of the handled receive ids, and clean
  sentinel `55 ADDPLAYER`s before and after.

## Result

**No crash and no desync.** Across all 17 shots the RC window stayed up (CPU 2–3%), and the socket
closed only at teardown. The receive parser stayed in step through the whole set, read from the
screen:

- the player count rose after each sentinel `55 ADDPLAYER`;
- the `62 RC_PLAYERRIGHTSGET` overrun (rights `i5:4294967295`, account `acct`, one short folder
  line) opened the player-rights dialog with every flag ticked and those values shown;
- the 4000-byte `74 RC_CHAT` line printed to the console after that dialog;
- nothing broke on the malformed `56`, `72`, `63`, `64`, `37`, `47`, `180`, `100`, `102`, `103`,
  the unknown ids (`60`, `66`, `200`, `223`) or the empty-body sweep.

So this build takes the rc-core set without a wedge; the open question is width-level parsing
(`rc-widths.plan`), which the screen canary answers and this run did not cover. **[lab]**

## Harness note

An RC sends to the server only when a user acts, so every post-login shot shows no client→server
traffic. `rccanary.py` reports these as `silent`, which here means "no crash, no disconnect", not a
wedged parser — the in-step evidence is the screen, not the wire. A future plan that drives an RC
reply (a scripted dialog action) would give `rccanary` a positive in-step signal on the wire.

## RC3 and RC2 2.05

Same round, same harness. **[lab]**

- **RC3** (`RemoteControl3.exe`, build 2015/10/31, `GSERV025`): logged in **type 6, gen 5**,
  account `super`, through the server list. It took the whole `rc-core` set **and** `rc-widths`
  with **no crash and no disconnect** (window alive at every shot; socket closed only at teardown).
  The width result is **unknown, not failed**: RC3's main window never paints under Wine — it is
  black from the base shot onward, before any inject — so the nickname canary can't be read from
  the screen. A Wine virtual desktop in the prefix registry is the likely fix.
- **RC2 2.05** (`RC2_2.05.exe`, 2006/12/20, `GSERV025`, GTK): could not be staged under Wine. GTK
  2.10 Pango fails font fallback ("All font fallbacks failed"), text draws as boxes, and the login
  never reaches the listserver. Its windows carry no X title (match with `xdotool --class`, not
  `--name`). Not a protocol result — a Wine/GTK environment problem.

So far the gen-5 RCs (2004 RC, RC3) take the core malformed set without crashing; the width-level
question is still open on both for want of a readable window.
