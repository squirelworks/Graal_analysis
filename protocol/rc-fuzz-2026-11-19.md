# Fuzzing the 2004 Remote Control: no crash on the rc-core set

Date: 2026-11-19. Tags: **[lab]** one run in the probelab. Evidence id: `RC-FUZZ-20261119`.

First packet-fuzz of a Remote Control client. Malformed and out-of-range server→client packets
were injected into a live RC session through `tools/probe/gen5probe.py`, with the harness added in
the same change (`tools/probe/lab/runrc.sh`, `rc-core.plan`, `rccanary.py`). Lab only, loopback
only; the run was isolated in its own network namespace and display and touched no other lab.

## Setup

- RC: the 2004 Delphi `RemoteControl.exe`, window title `Graal Remote Control 2004/01/17`, token
  `GSERV024`. Under Wine, behind the proxy. It logged in **type 6, generation 5**, account `super`
  — confirming the proxy needs no decode change for the type-6 RCs (the token sits where a version
  string goes). **[lab]**
- Server: the lab GServer-v2 fork (`gs2emu-73`) and `seihai-listserver`, the world bound to a
  second loopback address behind the proxy on `14804`. The `super` account needed `ADMINRIGHTS`
  and an open `IPRANGE`, not just a place on the staff list, or the server replied
  `You do not have RC rights.` (now set by `runrc.sh`). **[lab]**
- Plan: `rc-core.plan` — oversized string lengths, prop-stream run-off, huge counts, NUL/high
  bytes, unknown and deprecated ids, an empty-body sweep of the handled receive ids, and clean
  sentinel `55 ADDPLAYER`s before and after.

## Result

**No crash and no desync.** Across all 17 shots the RC window stayed up (CPU 2–3%), and the socket
closed only at teardown. The receive parser stayed in step through the whole set, read from the
screen:

- the player count rose after each sentinel `55 ADDPLAYER`;
- the `62 RC_PLAYERRIGHTSGET` overrun (rights `i5:4294967295`, account `acct`, one short folder
  line) opened the player-rights dialog with every flag ticked and those values shown;
- the 4000-byte `74 RC_CHAT` line printed to the console after that dialog;
- nothing broke on the malformed `56`, `72`, `63`, `64`, `37`, `47`, `180`, `100`, `102`, `103`,
  the unknown ids (`60`, `66`, `200`, `223`) or the empty-body sweep.

So this build takes the rc-core set without a wedge; the open question is width-level parsing
(`rc-widths.plan`), which the screen canary answers and this run did not cover. **[lab]**

## Harness note

An RC sends to the server only when a user acts, so every post-login shot shows no client→server
traffic. `rccanary.py` reports these as `silent`, which here means "no crash, no disconnect", not a
wedged parser — the in-step evidence is the screen, not the wire. A future plan that drives an RC
reply (a scripted dialog action) would give `rccanary` a positive in-step signal on the wire.

## RC3 and RC2 2.05

Same round, same harness. **[lab]**

- **RC3** (`RemoteControl3.exe`, build 2015/10/31, `GSERV025`): logged in **type 6, gen 5**,
  account `super`, through the server list. It took the whole `rc-core` set **and** `rc-widths`
  with **no crash and no disconnect** (window alive at every shot; socket closed only at teardown).
  The width result is **unknown, not failed**: RC3's main window never paints under Wine — it is
  black from the base shot onward, before any inject — so the nickname canary can't be read from
  the screen. A Wine virtual desktop in the prefix registry is the likely fix.
- **RC2 2.05** (`RC2_2.05.exe`, 2006/12/20, `GSERV025`, GTK): could not be staged under Wine. GTK
  2.10 Pango fails font fallback ("All font fallbacks failed"), text draws as boxes, and the login
  never reaches the listserver. Its windows carry no X title (match with `xdotool --class`, not
  `--name`). Not a protocol result — a Wine/GTK environment problem.

So far the gen-5 RCs (2004 RC, RC3) take the core malformed set without crashing; the width-level
question is still open on both for want of a readable window.

## A pre-2002 RC (gen 2)

`rc8212001.exe`, "GServer2 Remote Control 2001/08/20", token `GSERV022`. This is the first real
client on the proxy's **gen-2** path (pre-2002 RCs log in `id 1 + GSERVxxx`, plain u16be+zlib, no
cipher). **[lab]**

- The login was decoded correctly: `C>S LOGIN type=1 gen=2 key=0 ver=GSERV022 account=super`, and
  the server logged `New login: super [RC] [GSERV022]`. The proxy decoded the whole server→client
  stream cleanly — welcome chat (74), staff guilds (47), status list (180), 103, and the periodic
  42 keepalive — confirming the gen-2 staff-login detection works against a real client, not just
  the selftest. **[lab]**
- The start dialog uses a direct address (it already held the loopback, `14804`, `super`), so
  connecting is a single OK click. "Connected at port 14804" and "Currently online: super" showed.
- `rc-core`: **no crash, no disconnect**, 41 packets injected; in step (the `72` opened the Edit
  Account window, the `62` the Account-rights dialog with the injected flags/account/IP range).

This build does not send `PLI_PLAYERPROPS` (2) right after login (it sends its nickname only on a
player-list action), so the plan's `wait c2s 2` gate is a short fall-through, not a hard wait.

## The NC socket embedded in a 2002 RC

`RemoteControl.exe`, "GServer2 Remote Control 2002/05/02", tokens `GSERV023` (game) and `NCL11012`
(NC) both present. This RC opens a second connection — the NPC-Control (NC) socket — to the address
the server hands it, so the NC *client's* receive handlers can be fuzzed through the same lab. The
NC socket is fronted by a separate proxy (`ncprobe`) on a third loopback so it is the only
connection that proxy carries. **[lab]** (Done with the NC-fuzz thread.)

**A harness bug — not a server bug — blocked the discovery step at first.** After the gen-2 game
login (`C>S LOGIN type=1 gen=2 ver=GSERV023`) the RC sends `PLI_NPCSERVERQUERY` (94). On the first
runs the server received it and never answered with `PLO_NPCSERVERADDR` (79). Tracing it settled the
cause: the handler runs correctly (the 94 body is exactly `location`, and no "unknown
PLI_NPCSERVERQUERY" line is logged), and the silent return is in `sendNCLoginToPlayer`'s guard
`if (!player->isRC() || !player->account.hasRight(PLPERM_NPCCONTROL))`. `isRC()` passes; the
NPC-Control right (`PLPERM_NPCCONTROL`) was the missing half — and that was our fault. `runrc.sh` wrote
`ADMINRIGHTS 1048575` into the super account, but the flat-file loader reads the rights bitmask from
the `LOCALRIGHTS` key (there is no `ADMINRIGHTS` key), so `adminRights` stayed 0. Pre-#97 `gs2emu`
builds (73, 76, 101a) always check the right, so they always dropped 79; a post-#97 build with
`npcrights=false` skips the check and sends 79. With `LOCALRIGHTS 1048575` in the account the server
answers 94 with 79 natively on every build tried (≈9 ms later), and the RC opens its NC socket. So
GServer-v2 is correct here — the earlier "server bug" reading was a harness key-name mismatch, now
fixed in `runrc.sh`. **[lab]**

**Result.** Once the RC opens its NC socket, `ncprobe` logs `conn 1 open` and the NC login
`type 3 token=NCL11012 account=super`; the real gserver accepts it (`New login: super [NC]
[NCL11012 (1.1)]`) and sends the Control-NPC packets (158, 42). The NC fuzz plan then ran on that
session: **45 server→NC packets injected, no crash and no disconnect** (RC alive at all 46 shots, the
NC socket closed only at teardown). The first runs reached this via a hand-injected `PLO 79`
(`s2c 79 s:<server-pid> t:<ns-ip>,<port>`) before the `LOCALRIGHTS` cause was found; with the harness
fix the server sends 79 on its own, so `RC_NC` now relies on the native answer (`RC_NC_INJECT79=1`
keeps the manual inject as a fallback for an old binary). The NC fuzz result stands either way.
