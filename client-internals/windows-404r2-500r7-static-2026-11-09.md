# Windows 4.04r2, 4.20r8 and 5.00r7: static follow-ups from November 2026

These are the research owner's retained-code reviews of Windows v4 and v5 engines, dated 9 November 2026. Each is static unless it says otherwise; no client, server or VM was run for them. The publication editor read sanitized drafts and their identity manifests, not raw code. Evidence IDs resolve in [the evidence index](../docs/evidence-index.tsv). Addresses, assembly and private paths stay with the evidence owner.

Inputs: the Windows 4.04r2 core is the original-carrier engine captured by earlier load-only work (derived analysis image SHA-256 `3de2dc7097350dc782e9844f3f5620e8475b726b3494b9e49ed621c578d766f2`). The 5.00r7 engine is the backup engine from the archive labelled 5.00r7 (SHA-256 `dde0fc851e8aaba165a83578745cf10372eca3786219e917966ab3230c7c6bf1`), the same input as [windows-500-event-queue.md](windows-500-event-queue.md); a backup file name does not authenticate a vendor original.

## 4.04r2 runs GS1 source natively

Evidence `W404-GS1-NATIVE-20261109` and `W404-GS1-REGISTRY-20261109`. **[bin]**

- The 4.04r2 core has a legacy source-script path, separate from the newer GS2 segment and dispatcher interface. A lazy helper builds a parsed program from a non-empty source buffer when one is needed, and otherwise reuses the prepared program.
- Preparation normalizes the source, finds semicolon-separated statements, parses them and runs a post-pass over statement and jump records. The normalizer handles `//` and `/* */` comments, recognizes closing braces and can insert a semicolon after one. Quoting, delimiters and malformed source are not specified by this pass.
- Execution walks the statement list. For each eligible statement it fetches a native handler through the statement's descriptor and calls it, advancing the position and honouring a stop condition. Context-mask checks can skip handlers.
- The startup registry in the retained startup dump holds **193 named command descriptors**. 172 have non-zero callbacks inside the native core, and their first 16 instruction bytes match the core image; the other 21 are zero in that captured state, which does not mean those commands are unsupported. The `if`, `for` and `while` descriptors point at the native condition handlers.
- `created` is not queued through the named-event delivery helper. On first run the execution helper adds `created` to the active event list and records initialization. This differs from the later GS2 rule that puts a creation action at the front of the pending queue. For several other recognized events the receiver checks an event-interest mask before activating the object, and it merges pending event lists by context; the exact grouping is not traced.
- The helper also keeps timeout and resume-position state. Its exact continuation and save/restore contract is open, so neither the 2.05 sleep nor the GS2 scheduler should be assumed for this build.

This confirms, from code, the GS1 weapon execution already observed in [live-behaviour-404.md](live-behaviour-404.md). It does not give the full command table, the meaning of the context masks, or the 2.05 truth rule for this build.

## 4.04r2 clocks

Evidence `W404-E301-CLOCK-20261109`. **[bin][cap]**

- The core's `getTicks` pointer is `GetTickCount`, matched against the named export table in the same retained startup capture. `getHighPrecisionTime` and the registered `timevar2` scale that value by 0.001; despite the name, they do not use the performance counter.
- The legacy `timeout` property stores a count of service passes. For ordinary finite values the setter clamps negatives to 0, multiplies by 20, adds 0.0001 and floors; the getter multiplies the count by 0.05. The legacy script service decrements a positive count once per call and queues `timeout` when it reaches 0. Overflow and non-finite values were not checked.
- A separate GS2-style pass sets its global script clock from the scaled tick count, then adds 0.05 on each later pass. The player-update path reaches this pass through a helper. The runner subtracts the clock change from the remaining sleep or timeout and queues `istimeout` below 0.0001; scheduled events compare their deadlines with the same clock.

So this core has three distinct notions of time: elapsed ticks, pass-count time and legacy countdown units. None of this measures the actual update rate or shows a 50 ms wall-clock sleep under load; Appendix E#301 stays open.

## 4.04r2 tile sheet layout

Evidence `W404-E102-20261109`. **[bin]**

The tile draw path computes the base sheet position as `column = (id % 16) + floor(id / 512) × 16` and `row = floor(id / 16) % 32`, both times 16 pixels; the image-update invalidation path computes the same. Optional tiledef remapping is applied afterwards, and the host draws a 16 × 16 rectangle. This is code support for the 512-id block layout in Appendix E#102 rather than the older 128-column formula. For example id 16 is pixel (0, 16) here, not (256, 0). Other builds and custom tile definitions were not checked.

## 4.04r2 binary level records

Evidence `W404-E603-E604-20261109`. **[bin][file]**

- The binary-section reader does not use one whole-tile rule for every record. Link boxes are parsed as floating point; arrival fields stay text, defaulting to the player's coordinates. Baddy positions come from raw bytes; NPC, chest and sign positions come from bytes minus 32. Those byte paths give whole-number coordinates without half-tile scaling.
- The sign reader stops after a line shorter than two bytes, or at end of file. It does not itself recognize `HEIGHTS`. The ordinary offline binary reader calls it and returns; the separate web-level cache reader follows it with a heights reader, and the matching cache writer inserts a blank separator and an optional heights block. That cache behaviour does not apply to all offline files.
- A read-only decode of nine archive-labelled Mac 4.04r2 tutorial `GR-V1.03` files found 24 links, 11 NPCs and one sign, with no trailing bytes, baddies, chests or trailing heights block. These files support only part of the review.

E#603 and E#604 remain partly open: the cross-magic field examples and the 2.05 / 2.31 / server sign-count comparison are still missing.

## 5.00r7 sends id 11 when throwing

Evidence `W500-E4-THROW-20261109`. **[bin]**

In the 5.00r7 backup engine, the throw/release path for a carried object creates the local thrown object, clears the player's carry state and, when a game connection exists, calls a wrapper that sends client message **11** (`PLI_THROWCARRIED`) with an empty body. The ordinary encoder writes id + 32, the body and a newline. A property-18 broadcast in the same wrapper is a different thing and must not be read as the message id. This settles the Appendix E#4 discrepancy for this engine: the earlier wrapper list missed 11. It is a call-path read, not a capture; server acceptance was not tested, and the adjacent patched engine (eight bytes different) was not checked separately.

## 5.00r7 script container and cache

Evidence `W500-SCRIPT-INTERFACE-20261109`. **[bin]**

- The script setter reaches a decoder that reads ordinary **big-endian 32-bit** segment type and length fields, not GSHORT or GINT. Types 1–4 are the event mask, the function table, strings and instructions. The reader stops at an unknown type or a failed read; a safe policy for every malformed body is not claimed.
- In the function table, a `public.` prefix (7 characters removed) sets visibility 1, and `publicsoap.` (11 removed) sets visibility 2; the default is 0. Visibility 2 is distinct stored metadata, not proof of a remotely callable SOAP service.
- `GRESCR01` is a disk-cache wrapper. The reader's success output starts false. With a non-zero expected CRC, the stored body is checksummed **before** it is transformed, and a match sets success. A zero expected CRC skips the comparison, can still transform the body, and leaves success false. The weapon and class callers branch on that success flag, so "returned bytes" and "accepted cached script" are different conditions.
- The writer transforms a copy of the body and writes the magic plus transformed bytes only for cache flag 1; the reader rejects other flags and a missing key before touching the disk.
- On a cache miss the weapon helper sends logical **158** with the name. The class helper sends logical **161** with a five-byte value and then the name; its caller passes the stored-body checksum, so the generic table's `modtime` label does not describe this path. An alternative connection mode sends `getweapon` / `getclass` events instead of packets.
- The older description of PLO 140 says the body is "plain text". For the decoded-container path traced here, treat it as unencrypted script bytes until source text is shown.

## A Windows 4.20r8 3D plug-in candidate

**[file][bin]** A Windows 3D DLL recovered from an archive labelled 4.20r8 (SHA-256 `afc288bfa58a0acd285d349379c5e5ad465c5ee067be574b988df10161b4da55`) fills the gap noted in `torque/wire-by-build.md`, where the 4.20r8 upload had no `Graal3DEngine.dll`. The DLL has no version metadata, so the archive label is unverified.

- Its connect request writes `Graal3D` followed by protocol **24** as both current and minimum version, and its accept reader requires exactly 24.
- The class-table writer emits two types, with 12-bit type and class-id fields and names. The stored CRC entry for group 0 is all ones; no live value was captured.
- It registers Graal's `GameObject` as a networked class, resolves controlled ghosts as that class and builds received ghosts into the mission group. Its mission start has two phases, ghost download and then lighting. Login steps: 2 ghost download, 3 lighting, 4 lighting done, 5 the initial controlled object, 6 after TCP downloads finish and the 3D GUI is selected, the same sequence as `torque/4208-g3d.md`.

These observations are bounded to this one DLL. They do not replace the Mac 4.20r6 protocol 21 result, authenticate the label, give the full class set or prove compatibility with 5.12. No 3D session was run.
