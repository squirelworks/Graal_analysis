# Lab: 2.00 walking speed, 2.05 chest sides, 2.05 offline re-entry (2026-11-13)

`[lab]` Three manual cells measured with the original Windows clients 2.00 and 2.05 rev2 under Wine in a Debian lab VM,
headless (Xvfb), in a network namespace that reaches only the loopback address. Server for the online runs: `seihai-gserver`
commit `0f53796` with a logging-only patch, port 14802; listserver on 14900 and 14921–14923. 2.00 needed an `objects.dat`;
the same-checksum copy from the 2.05 rev2 asset set was used. Scripts, logs and screenshots are kept by the owner.

## 2.00 walking speed

| Build | Step | Steps apart (median) | Speed | Runs |
| --- | --- | --- | --- | --- |
| 2.00 | 0.5 tile (all 640 logged position changes over 15 timed walks) | 49.9–51.4 ms | 9.3–10.0 tiles/s, so 10 tiles/s nominal | 6/6 with the VM quiet |
| 2.05 rev2 (control, run just before) | 0.5 tile | 49.9–51.2 ms | 9.55–9.94 tiles/s | 6/6 |

- 2.00 walks like 1.x and 2.05: half a tile per 50 ms tick.
- On the wire both clients send X and Y about every 100 ms, so the server sees 1-tile deltas.
- With the VM heavily loaded, 2.00 slowed sharply (steps 100–870 ms apart, 9 runs) while 2.05 rev2 kept 50 ms steps. That
  fits 2.00 moving once per drawn frame without catching up on lost time, but this run does not prove it. **[lab][inf]**

## 2.05 rev2: which sides open a chest

| Approach | Opened | Runs |
| --- | --- | --- |
| from below, facing up | yes | 6/6 |
| from above, facing down | no | 0/6 |
| from the right, facing left | no | 0/6 |
| from the left, facing right | no | 0/6 |

- 24 attempts, each on a fresh chest. On the side that works, `PLI_OPENCHEST` (20) is sent with the chest's tile x and y.
- The chest opened as soon as the player walked into it from below, 0.3 to 0.75 s into the walk, before any action key.
  The action key is not needed in 2.05 rev2. Pushing against the other three sides and pressing the action key sent nothing.
- So 2.05 rev2 has the same one-side rule as 2.22.

## 2.05 rev2 offline: re-entering a level

Training mode with no server. Own local levels were loaded with the client's F5 load-level dialog.

- Each run lifted and threw one bush, cut another with the sword, left through a link and came back. Both bushes were still
  gone: 3/3 (one run waited 60 s in the other level). An untouched bush was still there, and the level files on disk were
  unchanged.
- Loading the same level name again with F5 also showed them gone: 2/2.
- So 2.05 keeps the edited level in memory for the session and does not reload it from disk on re-entry. Offline, a cut
  bush does not come back. This settles App. E#318.
