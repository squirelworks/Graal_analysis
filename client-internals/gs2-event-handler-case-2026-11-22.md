# Event-handler case matching in selected inputs

Date: 2026-11-22. Static source, selected instructions and bounded data reads; no native client was executed for this study. **[bin]**

This follows a separately retained 4.20r8-labelled Windows input, the selected archive-labelled Windows 5.00r7 backup and the exact recorded Linux 6.03r7 x64 executable. Archive labels do not authenticate releases. The Linux carrier matches its static export, not independently every historical lab process. Owner-held evidence: GS2-EVENT-CASE-20261122 in the [evidence index](../docs/evidence-index.tsv). **[bin][inf]**

The question is whether selected event-handler lookup distinguishes names such as `onTimeout` and `onTimeOut`, or capitalization within `onActionServerSide`. Finding such strings, folding a scheduled-event name or following an ordinary function call would not settle the event-specific lookup. The chains here reach candidate handler selection from the event consumer. **[bin][inf]**

## Older selected Windows input

The selected self-event route calls an event-specific function scanner. It folds the requested event name and the suffix of candidate function names with the recognized `on` prefix, then compares the folded suffixes. The prefix's literal spelling is independently bound to this input. The scanner also follows joined programs and adjusts matched integer instruction entries. This is a handler-candidate comparison, not merely queue-name matching. **[bin]**

The selected case helpers include a locale/state-dependent branch that this study does not bind to an observed runtime locale. The evidence therefore establishes explicit folding operations on this path, rather than a universal character mapping or an executed spelling matrix. **[bin][inf]**

## Selected Windows backup

Its self-event consumer reaches a separate scanner. That scanner constructs the recognized prefix plus a folded requested name, folds each candidate's complete function name and compares the resulting names. It collects matching function objects through its own and joined-program scans. Its `on` literal is independently bound, rather than borrowed from the older input. **[bin]**

This differs from the older suffix-comparison/integer-entry implementation. The selected locale-sensitive helper state, all catch/resume branches and duplicate-definition policy are not completely established. Neither scanner proves that a gameplay action queues a particular event. **[bin][inf]**

## Exact recorded Linux input

The actual event helper forms a handler name with its independently bound `on` prefix and selects one of two lookup paths. The ordinary path searches the program's function hash and recursively visits joined programs. The multi-handler path iterates candidate functions and collects matches recursively before eligible execution. **[bin]**

For the ordinary path, function registration and query hashing explicitly map ASCII uppercase letters to lowercase before the same hash recurrence. Bucket lookup checks equal name lengths and applies the same ASCII fold to both candidate and query bytes. This closes the insertion/query consistency requirement; a folded query hash alone would not have proved a match. **[bin]**

The multi-handler path uses a library case-insensitive comparison instead of that bucket lookup. These are separately followed mechanisms. Neither proves Unicode equivalence, arbitrary locale behavior or one case policy for every object/property namespace. **[bin][inf]**

## Meaning and remaining boundary

The Linux paths explicitly match the shown ASCII capitalization changes. The selected Windows paths perform the described folding, whose complete character mapping remains qualified by the unbound helper state above. The studies do not establish that every API accepts both prefixed and unprefixed requests, or that an uppercase `ON` prefix follows every same route. Source compiler normalization and event-production sites are separate questions. **[bin][inf]**

Case matching also does not guarantee that both case-only duplicate definitions run, that registration succeeds, or that an event passes masks, queue, owner, resource and execution gates. The [broader spelling-by-client question](gs2-vm-quirks-by-version.md#11-still-open) remains partial: this is a selected static lookup result, not a complete native runtime matrix or authenticated behavior for every version. **[bin][inf]**
