# Graal 2.00 (and rev1-3, 2.01-2.05): login, tables, lab setup

Sources: the 2.00 decompile and the four 2.00 builds from the Drive clients set (`../drive-clients-inventory.md`). All four 2.00 builds give the same token and the same tables. Derived facts only.

## Login string (gserver)
- Built from: GCHAR(random key & 0x7F) as the key byte, then the 8-char token `GNW24011` (assembled character by character from immediates, so a plain text search finds nothing), then GCHAR(len account) + account, GCHAR(len password) + password. It is sent through the client's send method with packet type 0 (same "type 0, key byte, token, account, password" shape as 2.05 and 2.17). Account and password are NOT hidden or hashed in 2.00.
- The key byte seeds the gen-3 stream cipher framing used afterwards (zlib + one junk byte per message after the first, as documented for 2.05 and 2.17). No new framing in 2.00.
- Tokens for the whole 2.00-2.1 family: `version-profiles/version-tokens-by-build.tsv` (all confirmed from the binaries) and `../version-tokens.md`.

## Server -> client ids handled (2.00)
- Dispatch bound 0x9b; 53 ids: 0-45 (including both 25 and 26), 75, 100, 150, 151, 153, 154, 155. No 46-49, 156, 165-169, 68-69.
- Growth: 2.01 +46, +156 (55 ids); 2.02 +47 (56); 2.03 +48, +165 (58); 2.04 drops 26 (25 stays) and adds 166; 2.05 +168 (59); the 2.1 test builds +49, +169 (61). Full list: `version-profiles/plo-handled-ids-by-build.tsv`.
- `PLO_SIGNATURE` (25) is handled in 2.00 already, so the kill-switch exists from the first 2.x client.
- `PLO_NPCACTION` (26) is handled by 2.00-2.03 and dropped in 2.04. Later clients ignore it. Its payload is not decoded here.

## Client -> server ids the 2.00 binary can send
0-24, 26-30, 32-34, 80, 81. Compared with 2.05 rev2 (0-24, 26-30, 32-38, 80, 81): 2.00 lacks 35-38; 35 and 36 arrive in 2.01, 37 in 2.02 rev2, 38 in 2.03. Table: `version-profiles/pli-sent-ids-by-build-20x.tsv`. Method: call sites of the client's send method with a constant id. The 2.05 rev2 result matches the id set already in `protocol/packet-ids.md`, so the method is sound. Id 6 shows up in every build and may be a false positive of the scan.

## Token allow-list
- A GServer-v2 gserver has a text allow-list of tokens. For a lab, a **config entry** for `GNW24011` in that list is enough. No binary patch is needed on the server, and none is needed in the client for the login itself. (Earlier notes, `version-profiles/version-coverage-2026-10-24.md`, said an allow-list patch; that meant this config entry.)
- Still needed by the 2.00 client: a list server it can reach. The list host is DES-hidden inside the exe (scheme in `../des-and-hidden-strings.md`, port 14921 per `protocol/listserver.md`), and 2.00 does not read `arrays2.dat`. For a lab, resolve that name to the lab listserver and run the lab listserver on 14921, or patch the hidden string.
- **Partly observed (batch b2, `07-lab-findings-46-186-200.md`):** the 2.00 client sends one plain zlib frame, `GCHAR 0` + `newmain` + LF, with no account or password, then makes no second listserver connection and goes straight to the gserver. 2.00 accepted a 2.17-style two-frame list reply, but that reply was **synthetic** (a lab-only forwarder translated the request). What a real 2.00-era listserver sends is still unobserved. Table: `version-profiles/lab-200-listserver-handshake.tsv`.

## Does it run?
Yes under Wine 10 (separate prefix, loopback-only lab network, private display), with a data-file caveat. The Drive 2.00 exe alone stops with "Cannot open file commands.rtf", because the Drive folder holds only the exe. Placing the data files of a NewMain 26 folder (commands.rtf, images, languages) beside it makes it reach its start screen. A copy of the 2.22 data folder also works for the start screen and login, except that `objects.dat` is missing there and 2.00 needs it (nickname box, Training / Options / Start). See `../drive-clients-inventory.md`.
