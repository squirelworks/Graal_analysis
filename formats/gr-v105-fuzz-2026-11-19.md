# GR-V1.05 levels and PLO_BOARDLAYER (107): fuzz lab

Date: 2026-11-19. Tags: **[lab]** for live runs, **[srv]** for our lab gserver's source.

Follows [`gr-v105-500r7.md`](gr-v105-500r7.md), [`gr-v105-500r7-cache-lab.md`](gr-v105-500r7-cache-lab.md)
and [`gr-v105-empty-tiles-2026-11-16.md`](gr-v105-empty-tiles-2026-11-16.md). Loopback lab only.
Captures, screenshots and cache files stay off-repo.

## Method

| Piece | What was used |
|---|---|
| Levels | 16 synthetic levels from [`grv1-decoder/grv105gen.py`](grv1-decoder/grv105gen.py): a hub plus 15 cases (2, 3 and 8 layers, count 1, count 0, RLE, checkerboard, explicit 4095, 4095 on layer 0, HEIGHTS, count 200 with two boards, raw count byte `0xff`, a cut board, an NPC, and a GR-V1.04 control). Layer 0 is all grass, and the painted cells use tile 332. |
| Server | Our lab gserver `gs2emu-73` (seihai-gserver-v2 `fbd30767`, GS2Emu 4.0.0-beta), which loads GR-V1.05 and sends each extra layer as PLO_RAWDATA + 107 |
| Clients | Windows 4.20r8, 5.12 and 5.24r4 under Wine; native Linux 6.03r7 |
| Probe | `gen5probe.py` with `PROBE_FULLHEX=107,100,7`; plan [`boardlayer.plan`](../tools/probe/lab/boardlayer.plan), written by `mkboardlayer.py` (37 steps, bomb canary after each) |
| Level visits | An injected chat `warpto 30 32 LEVEL`, with `warptoforall` on in the world copy. An injected PLI_LEVELWARP (0) does not move the client, because the server sends no PLO_PLAYERWARP back. |

Runs: `gr105-lv524-*`, `gr105-lv512-*` (level walks) and `gr105-bl524-*`, `gr105-bl512-*`,
`gr105-bl603-*`, `gr105-bl420-*` (107 injects), in a private copy of the Wine lab tree.

## The lab gserver misreads every GR-V1.05 file **[srv][lab]**

The loader reads the layer count with `readPackedIntegral<1>()`. In that template the width guards are
written `if constexpr (C <= 2)`, `C <= 3`, `C <= 4` and `C <= 5`, where they should be `C >= …`. So a
one-byte read consumes **five** bytes, and every board starts four bytes late.

- Re-decoding our files with a four-byte skew reproduces, bit for bit, all 4096 layer-1 cells the server
  sent and the three stray cells at the end of layer 0.
- Because of the skew, layer 1 reaches the client as RLE garbage, a level with 8 layers sends only 2
  layers, and the painted patches never arrive.
- The same call appears elsewhere in the file reader, and the bug is still on the fork's current head.

So the lab server cannot yet show what a correct GR-V1.05 serve looks like. The wire and draw results
below come from the injected 107 packets, not from served levels.

## Two levels crash the lab gserver **[lab]**

`fz105-0` (count 0) and `fz105-base4095` end the server with an uncaught
`std::filesystem::filesystem_error` ("File name too long"). Board bytes are read as a link line, and the
existence check on that huge "level name" throws. This happened on both runs that loaded the two files.
`trunc`, `many-short` and `count255` do not crash it.

## PLO_BOARDLAYER (107) on the client **[lab]**

| Question | Result |
|---|---|
| Which clients draw 107 | **All four**: 4.20r8, 5.12, 5.24r4, 6.03r7. 4.20r8 is not a control for 107 (it has had 107 since 4.11, see [`v4x-windows-403r3-411.md`](../protocol/v4x-windows-403r3-411.md)); only the GR-V1.05 *file* magic is new in 5.00r7. |
| Header | Five **raw** bytes: layer, x, y, w, h. A GCHAR (+32) header lands off the board, so nothing shows. |
| Tiles | Little-endian 16-bit, w × h of them. Big-endian and GSHORT bodies draw the wrong tiles. |
| Body length | The client keeps only w × h cells. Extra tiles are skipped, and the next packet still parses (the canary lands). |
| RAWDATA wrapper | Not needed, unless the body holds a `0x0a` byte (for example layer 10, x 10, or a tile with a `0x0a` byte). The server always wraps it, which is the safe form. |
| Layers | Every layer 0–255 draws. |
| Tile 4095 | Draws as **tileset cell 4095** (a dark tile), not as blank. |
| Tile `0xFFFF` | Draws as **empty** (the layer below shows through). |
| Layered PLO_BOARDMODIFY (7) with a GCHAR(layer+64) marker | No crash and no reply; the canary lands. |
| Crashes or replies | None on any 107 or 7 variant, on any client. |

On 4.20r8, 5.12 and 6.03r7 the bomb canary landed on every step. 5.24r4 under Wine blacks out the board
after the first 107 in both runs, and its canary misses fell on different steps each time. We read those
misses as repaint noise, not parse failures.

### What this settles

- **Empty upper-layer cells.** On disk an empty cell is 4095 ([`gr-v105-empty-tiles-2026-11-16.md`](gr-v105-empty-tiles-2026-11-16.md)),
  but on the wire 4095 draws as a real tile. A server has to turn on-disk 4095 into `0xFFFF` before it sends a layer.
  Our lab gserver's loader already does this on layers above 0, for literal codes and both run kinds.
  This closes the "draw of tile 4095" question for injected layers. **[lab][srv]**
- **Heights.** No heights packet is ever sent, for either the HEIGHTS level or the GR-V1.04 control. The
  lab server's loader reads heights only for 1.05, and nothing sends them. **[lab][srv]**

## Other results **[lab]**

- The `fz105-npc` level's NPC still loaded and ran despite the skew.
- The 5.x clients wrote no GR-V1.05 web-level cache entry in these runs. Each visited level left only a
  script-cache `.code` file. That differs from the 5.00r7 cache lab, where the server sent correct layers.
