# Preagonal GS2 compiler and VM

Study read on 2026-11-07 of the Preagonal org (`github.com/orgs/Preagonal/repositories`). The two language repos are [Preagonal.Scripting.GS2Compiler](https://github.com/Preagonal/Preagonal.Scripting.GS2Compiler) at `7878bc5` (2026-06-29, "Unify branch tips after parser parity fix") and [Preagonal.Scripting.GS2Engine](https://github.com/Preagonal/Preagonal.Scripting.GS2Engine) at `f8b5f13` (2025-01-01, "Add coverage status"). No program was built or run. Nothing here is copied from those trees.

This is a third-party reimplementation. It is not a reading of a Graal client or of an official server, and it does not settle → the open GS2 language gap in the manual (App. E#207). Where it disagrees with a note we already have, both sides are tagged.

## Pipeline

The compiler accepts GS2 source text. `Interface.CompileCode` takes the source, a type string (default `weapon`), a name string (default `npc`), and a flag for a header (default on), and returns success, an error string, and a byte array (`Interface.cs` lines 5–6, `CompilerResponse.cs`). `GS2Compiler.Compile` parses, emits, and optionally wraps a header (`GS2Compiler.cs` lines 10–23). The parser and emitter that produce those bytes are the hand-written ones in that file. An ANTLR lexer and parser (`Grammar/GS2Lexer.g4`, `Grammar/GS2Parser.g4`) are checked only for "this source parses" (`AntlrGrammarTests.cs`). They are not what `Compile` calls.

The engine library does not parse source. `Script` is constructed from a bytecode file or a byte array (`Script.cs` lines 32–65). The engine's tests and sample program take the compiler's bytes and then call a function by name: the test project references a NuGet package `GS2Compiler` 1.1.4 and calls `CompileCode` before `new Script` (`GS2Engine.UnitTests.csproj`, `ScriptMachineTests.cs` lines 40–51). The tests are written as that sequence: source, the compiler's bytes, then the VM (`ScriptMachineTests.cs` lines 40–51). The VM does not parse source. The header length the compiler writes and the length the engine reads differ; that is under the segment list below.

The bytecode body is four big-endian segments, then one trailing newline byte (`GS2Compiler.cs` `ToArray`, lines 1855–1873; engine reader `Script.cs` lines 130–315):

| Segment type | Body |
| --- | --- |
| 1 | one 32-bit word. The compiler always writes zero (`GS2Compiler.cs` line 1860). The engine stores it and does not read it again (`Script.cs` lines 163–169). |
| 2 | function table: for each function, a 32-bit op index, then a NUL-terminated name. A `public.` prefix is stripped and the name is stored lowercased (`Script.cs` lines 172–194 and 368–369). |
| 3 | NUL-terminated strings. |
| 4 | opcodes. An operand is not an opcode. Marker bytes `F0`–`F2` are a string-table index (8, 16, or 32 bits). `F3`–`F5` are a signed integer of 8, 16, or 32 bits. `F6` is a NUL-terminated decimal (`Script.cs` lines 222–300). |

Op indices count opcodes, not bytes. The compiler appends one return opcode after the last opcode of the file (`ToArray` emits it before it patches forward jumps). A function that does not already end in `return` also gets a zero and a return, except a function whose name is `getPreviewSpriteCount` (`GS2Compiler.cs` lines 611–637). That exception is a parity special case in this compiler. It is not a language rule we have from anywhere else.

With the header flag on, the compiler prefixes the segments with the byte our packet table gives `PLO_NPCWEAPONSCRIPT` (140), a raw 16-bit big-endian length, and the ASCII `type,name,0,` (`GS2Compiler.cs` lines 1914–1923). The `0` is the save-to-disk field, forced off, with no key and no checksum after it. The engine's header check is a different length. If the first byte is 140's id, it reads two bytes as `(b0 − 32) << 8 + (b1 − 32)` (`TString.cs` lines 160–165, `Script.cs` lines 317–348). That is not a raw 16-bit length. It is also not the GSHORT in our codec note, whose two bytes are `(v >> 7) + 32` and `(v & 0x7F) + 32` **[srv]** (`protocol/codec-and-framing.md`). On a stream that does not start with that id, the same check reads the first segment-type word and, when the word is a known segment, returns without rewinding (`Script.cs` lines 321–333). `SetStream` does not rewind after that return (lines 134–136). This read did not run either program, so the mismatch is what the source says.

`PARITY.md` on the compiler tip claims 155 of 155 advanced fixtures match a baseline hash and a baseline size. `CORRECTNESS.md` in the same tree still records 39 of 155 hash matches on 2026-06-28. This read did not run the suite, so neither figure is confirmed here.

## Types, scopes, objects, events

Source types, from the hand parser and lexer (`GS2Compiler.cs` lines 1926–2061 and the grammar files): numbers (decimal or hex, optional fraction, no exponent), strings in double or single quotes, `true`, `false`, `null`, and arrays written with braces. `const` and `enum` are folded to numbers at compile time. A two-part name `A::B` whose first part does not start with `$` is an enum member, or the number 0 if that member is unknown (lines 522–529 and 1154–1156). Longer `::` names stay one identifier. Comments are `//` and `/* */`. `NL`, `SPC`, and `TAB` are the concatenation operator with a newline, a space, or a tab between the sides. `:=` is assignment. `<>` is inequality. `=<` and `=>` are the two comparisons. `int(...)`, `float(...)`, and `_(...)` are casts. Keywords cover `public`, `function`, `if`, `else`, `elseif`, `for`, `while`, `break`, `continue`, `return`, `new`, `with`, `switch`, `case`, `default`, `const`, `enum`, and `in`. There is no `do`/`while`.

A script is a list of constants, enums, functions, and statements. A function may be `public`, may be `object.name`, and may omit its body. For an object named `universe` the function-table string is the bare name, a comma, and `universe.name`, with `public.` on both parts when the function is public (lines 615–618).

The engine's stack values are number, string, variable, boolean, array, an array-start marker, player, function, or script (`StackEntryType.cs`). `null` is pushed as the number 0 (`ScriptMachine.cs` lines 276–278).

Names are lowercased on lookup. An unqualified variable is resolved in this order (`GetEntry`, lines 854–900): the temp map, then the optional reference object passed into `Script`, then a process-wide global map, then a process-wide object map. A miss becomes 0. The script's own fields are not on that list. They are reached by `this` or `thiso`, both of which push the script object itself (lines 800–805), and then by member access. Assignment inside a `with` writes the object on the with-stack. Otherwise a variable assignment writes the global map, unless the previous opcode was `temp`, which diverts the next assignment into the temp map (lines 456–487 and 817–820). `player` pushes the global object stored under the name `player`, or 0 when that entry is missing (lines 806–812). `playero` and `level` are recognised and do nothing (lines 813–816).

`new Type(name)` looks up a host class by name. A name that ends in `Profile` becomes their `GuiControl`; any other name is created by reflection (`GetInstance`, lines 831–851). A `new Type(name) { ... }` statement compiles to that construction plus a call by the name `addcontrol` for each nested `new` (`GS2Compiler.cs` around line 906). `GuiControl` is one hard-coded object with fields such as `active`, `canmove`, `extent`, and its own `addcontrol` (`GuiControl.cs`). That is this VM's host, not a map of Graal's objects.

A script is bound by constructing `Script` with the bytecode, an optional reference object, and a `ScriptType`: weapon 0, level NPC 1, class 2, player 4 (`ScriptType.cs`). There is no gani type. The host registers commands on a static map (`GlobalFunctions`); the sample program registers `echo`, `showimg`, `findimg`, and `getimgwidth` (`TestApp/Program.cs`). `AddObjectReference` puts a named object on the process-wide object map (`Script.cs` lines 501–507). Events are function names. `Call` lowercases the name, pushes the arguments in reverse, and runs that function (lines 398–448). Nothing in the bytecode marks `onCreated` or any other name as an event.

`settimer` is registered as a host command that waits `seconds × 1500` milliseconds and then runs `onTimeout` directly (`Script.cs` lines 106–114 and 465–493). `TriggerEvent("ontimeout")` does not run the function (lines 450–463). `sleep` is an opcode: the engine pops a number, multiplies by 1000, and delays (`ScriptMachine.cs` lines 225–228). There is no frame clock, no `timeout` property, and no `scheduleevent`.

## Control flow and the opcodes they named

These names are the project's own enum names (`Opcode.cs` in the engine, the private `Op` enum at the bottom of `GS2Compiler.cs`). They are not taken from a Graal binary in this read. Numeric values below are the ones both enums agree on, except where the engine omits a name the compiler still emits.

Control: `OP_SET_INDEX` (1) jumps to an op index. On the first call the engine starts at op 0, and a jump whose target equals the opcode count is diverted to the function that was requested (lines 43–54 and 81–94). Later calls start at that function's index. `OP_SET_INDEX_TRUE` (2), `OP_OR` (3), `OP_IF` (4), and `OP_AND` (5) are conditional jumps. `OP_CALL` (6) calls a script function, a host command, or a function stored on the current `with` object; an unknown name pushes 0 (lines 166–218). `OP_RET` (7) returns the top value, or 0. `OP_SLEEP` (8) delays as above. `OP_CMD_CALL` (9) increments a counter stored on the instruction; the loop-limit stop is commented out (lines 230–249). `OP_JMP` (10) is a no-op (lines 251–256).

The compiler also emits `OP_WAITFOR` (11) for `waitfor(...)`. The engine enum has no 11, and the switch's default is the same arm as `OP_NONE`, so that opcode does nothing.

Constants and stack: `OP_TYPE_NUMBER` (20), `OP_TYPE_STRING` (21), `OP_TYPE_VAR` (22), `OP_TYPE_ARRAY` (23), `OP_TYPE_TRUE` (24), `OP_TYPE_FALSE` (25), `OP_TYPE_NULL` (26), `OP_PI` (27), `OP_COPY_LAST_OP` (30), `OP_SWAP_LAST_OPS` (31), `OP_INDEX_DEC` (32), conversions to float, string, and object (33–36).

Objects and arrays the compiler emits, and what the engine does: member access (35), array end (37), `new[n]` (38), `setarray` (39, engine arm empty), inline `new` (40), `makevar` (41, empty), `new` object (42), inline conditional (44), assign (50), end of a parameter list (51), increment and decrement (52–53). The engine enum has no "object from string" opcode. The compiler does not emit one either.

Arithmetic that the engine runs: add, subtract, multiply, divide, modulo, power (60–65). Comparisons (70–75) and concatenation (`OP_JOIN`, 113) run. `OP_NOT` (68), unary minus (69), bitwise or (76), and bitwise and (77) are empty arms. The compiler also emits bitwise xor (78), bitwise invert (79), and shifts (101 and 102). The engine enum does not name those four, so they take the empty default.

Built-ins the compiler turns into their own opcodes, rather than a call by name (`GS2Compiler.cs` lines 1612–1649 and the call emitter around 1239–1301): `sin`, `cos`, `arctan`, `abs`, `exp`, `log`, `random`, `min`, `max`, `vecx`, `vecy`, `char`, `pow`, `getangle`, `getdir`, `arraylen` and `sarraylen` (size), `waitfor`, `sleep`, `setarray`, `makevar`, `format`, plus the casts and the string and list methods (`trim`, `length`, `pos`, `starts`, `ends`, `tokenize`, `size`, `clear`, `add`, `delete`, `insert`, `remove`, `replace`, and the rest of that enum). Of those, the engine actually computes `format`, `abs`, `sin`, `cos`, `arctan`, `vecx`, `vecy`, `join`, `starts`, and `size`. The other arms are empty, so a script that uses them compiles and then skips the operation.

`with` / `with` end (150–151) push and pop the with-stack. `for`-each (163) walks an array. `this` (180), `thiso` (181), `player` (182), `playero` (183), `level` (184), and `temp` (189) are the reserved objects above. The engine names `OP_PARAMS` (190) and does nothing with it. The compiler's enum has no `params` opcode, so a source name `params` is an ordinary variable.

Every other call, which is every game command (`echo`, `showimg`, `set`, and the rest), is `OP_CALL` by name. The opcode table does not list those commands. The host map does.

## Where this lines up with our notes

Tags: **[doc]** this tree, cited by file as above. **[srv]**, **[bin]**, **[src]**, **[inf]** are the tags already on our notes. Seihai's GS2 notes live in `squirelworks/seihai` under `documentation/`. They are cited by filename. Addresses in those notes are not repeated here.

Agreements:

- The thing that runs is bytecode, not the GS1 text the classic clients run. Our manual says 4.x and later receive GS2 compiled, and that 2.05 never sees that path (`manual/08-scripting/03-gs2-language.md`, `04-gs2-bytecode.md`) **[bin][srv]**. Preagonal's engine matches that split: source stops at the compiler.
- NPC bytecode on the wire is the segment file with no header. Seihai's `documentation/gs2-receive.md` says GServer-v2's header helper is only for class and weapon scripts, and NPC bytecode (message 131) is the four segments plus the trailing newline **[src]**. Preagonal's header flag defaults on for a weapon, and off leaves the four segments. That split of the compiler matches. The compiler's header is 140's id byte in front of a list shaped like message 197 (`type,name,saveToDisk`) that stops after save-to-disk **[doc]**. Our packet table says 140 is a GSHORT length and then the script, and 197 carries the key and the checksum as well **[srv]** (`protocol/packet-ids.md`, `manual/00-conventions.md`).
- The segment order, the `F0`–`F6` operands, op indices, the `public.` prefix, the `universe` comma name, the implicit return, and "game commands are calls by name" match Seihai's `documentation/gs2-opcodes.md` and `documentation/gs2-grammar.md`, which summarise `gs2-parser` **[src]**. Constants and enums disappear at compile time in both readings. `params` is not given its own opcode by either compiler **[src]** (`gs2-opcodes.md`).
- Event names are ordinary functions. Seihai's grammar note says the same **[src]**. Our §8.3.3 names (`receivetext`, `onRCChat`, `action<name>`, the connection events, `onGraal3DLoginStep`) are names a host would call. Preagonal does not special-case any of them **[bin]** for the list (`manual/08-scripting/03-gs2-language.md`), **[doc]** for the absence.
- `|=` and `&=` do not compile. Seihai's grammar note says the `gs2-parser` scanner returns tokens for them and the grammar has no rule **[src]**. Preagonal's emitting lexer does not even make them one token; the unused ANTLR lexer does, and that parser's assignment rule still omits them (`GS2Parser.g4` assignment alternatives, `AntlrGrammarTests.cs` token test).
- GS1 event flags in segment 1 are written as zero, which is what `gs2-opcodes.md` records for `gs2-parser` **[src]**.

Disagreements, and gaps where our notes are silent:

- **This tree is not the client.** The manual leaves GS2 syntax, the standard library, the event model, and the bytecode format open (App. E#207) **[inf]** (`protocol/graphics-movement-bytecode.md`). Preagonal does not close that. Seihai's executor note is a separate reading of the 3.153 client **[bin]** (`documentation/gs2-executor.md`) plus `gs2-parser` **[src]**. Where Preagonal and that note differ, the client reading is the one Seihai tagged **[bin]**, and Preagonal is only **[doc]**.
- **Null, `this` / `thiso`, and lookup.** The 3.153 reading pushes a null object, treats `this` and `thiso` as the same store but as real objects, and looks an unqualified name up through the with-stack, the function's locals, the script object, the level, then the global object. `playero`, `level`, `client`, `clientr`, and names starting with `$` are handled before that search **[bin]** (`gs2-executor.md`). Preagonal pushes 0 for null, pushes the same script object for `this` and `thiso`, leaves `playero` and `level` empty, and does not know `client` or `clientr` as opcodes. Unqualified assignment goes to the process-wide global map, not the script **[doc]**.
- **`OP_JMP` and the loop counter.** The 3.153 reading uses `OP_JMP` to record the stack height for the return, and `OP_CMD_CALL` stops the script past the loop limit **[bin]**. Preagonal's `OP_JMP` does nothing, and the limit throw is commented out **[doc]**. The 10 000 figure Seihai uses is the `gs2-parser` enum comment, and Seihai says the client's own constant was not read **[src]** (`gs2-executor.md`).
- **Timers.** GServer-v2 counts `settimer` and `scheduleevent` in frames of one twentieth of a second, and the timer function is `onTimeout` **[src]** (`documentation/gs2-commands.md`). The 3.153 table has `settimer(t)`, a `timeout` property, and `scheduleevent` **[bin]** (same note). Preagonal's `settimer` is a wall-clock wait of one and a half times the argument, `sleep` is a thousand milliseconds per unit, and `scheduleevent` is absent **[doc]**.
- **Opcodes the compiler emits and the engine skips.** `waitfor` is opcode 11 in both `gs2-parser` and this compiler **[src]** (`gs2-opcodes.md`) **[doc]**. Seihai's executor note says the 3.153 VM has no case for it either **[bin]** (`gs2-commands.md`), so the skip agrees with that client reading and disagrees with a VM that claimed to run `waitfor`. The empty arms for `not`, unary minus, bitwise operations, shifts, `int`, `random`, and most string and list methods disagree with the 3.153 reading, which runs those **[bin]** (`gs2-executor.md`, `gs2-commands.md`). They also disagree with this project's own compiler, which emits them.
- **First call versus top level.** Seihai runs top-level code from op 0 as its own pass, then calls an event at its index **[src]** (`gs2-executor.md`, Seihai's executor section). Preagonal's first `Call` starts at op 0 and hijacks a jump aimed at the end of the file into the requested function **[doc]**. A top-level statement that the compiler placed after the functions is not run by that rule.
- **Header length.** The compiler writes a raw 16-bit length after 140's id byte. The engine reads a biased short, `(b0 − 32) << 8 + (b1 − 32)`. Our GSHORT is a different bias, `(v >> 7) + 32` and `(v & 0x7F) + 32` **[srv]** (`protocol/codec-and-framing.md`). The three encodings are three different layouts **[doc]**. The engine's no-header path also consumes the first segment-type word before the segment loop **[doc]**. Neither was executed in this read.
- **Script kinds.** Message 197's types are weapon, npc, class, and gani **[srv]** (`protocol/packet-ids.md`). Preagonal's enum is weapon, level NPC, class, and player **[doc]**. Player is an extra kind. Gani is absent.
- **Objects.** The 4.x engine exposes its objects to GS2, and `new` of a control plus `addcontrol` is the shape in the grammar note **[bin]** (`graal3d/torque-engine-4x.md`) **[src]** (`gs2-grammar.md`). Preagonal binds `new` by C# reflection and one `GuiControl` type **[doc]**. That host is not the 4.x object set.
- **`getPreviewSpriteCount`.** Only this compiler skips the implicit return for that one name **[doc]**. `gs2-opcodes.md` does not record that exception **[src]**.
- **NPC library.** `npc-library/` is GS1 source scraped from levels, plus the 2.05 command tables. It does not describe this bytecode. From 4.x the clients use GS2 (`npc-library/scripts/README.md`). The command-by-build chart says `with` is a GS1 command in 3.04 only, and that in 4.04 rev 2 the `with` string sits with the GS2 compiler **[bin]** (`npc-library/gs1-commands-by-version.md`). Preagonal's `with` is the GS2 statement, which agrees with that placement and says nothing about the 3.04 GS1 command.

## What a shared Seihai VM has to do

The Rust VM belongs in `squirelworks/seihai`, in the existing `seihai-core` scripting module (`crates/seihai-core/src/scripting/gs2/`), which already reads this bytecode and runs a subset (`documentation/gs2-opcodes.md`, `documentation/gs2-executor.md`). The client and the MIT servers (`seihai-gserver`, `seihai-npcserver`, and the others) take that crate by git tag. It does not belong in the GPL forks, and it is not a C# port laid out like Preagonal's files.

Behaviours that one shared machine has to cover, taken from our notes rather than from Preagonal's types:

- Read the four-segment file, including the operand markers and the function and string tables, and accept the same bytes with or without the class/weapon header. NPC message 131 is the headerless body **[srv][src]** (`manual/08-scripting/04-gs2-bytecode.md`, Seihai `gs2-receive.md`).
- One stack machine for client and server: the control opcodes, calls, returns, a sleep that yields back to the host, arithmetic, comparisons, conversions, member access, assignment, arrays, strings, and the built-ins the compiler gives their own opcodes. Every other name is a host command, so the client and the NPC server can supply different hosts without a second interpreter.
- One object model: `this` and `thiso` share a store, with `player`, `playero`, `level`, `temp`, `params`, a `with` stack, function locals, and a global object, in the order the 3.153 reading describes **[bin]** (Seihai `gs2-executor.md`). Events are functions the host calls by name, including the names in §8.3.3.
- Timers on the one-twentieth-second frame clock, including `settimer`, `timeout`, and `scheduleevent` **[src][bin]** (Seihai `gs2-commands.md`), so the NPC server and the client do not each invent a delay.
- Binding: an NPC, a weapon, a class, or the player owns a script; a class join shares that class; a public function is callable from another script; `new` and `addcontrol` are host objects.

A compiler, if Seihai later grows one, only has to emit that bytecode. The shared crate is the reader and the machine. This pass does not start that crate.

## What this does not settle

App. E#207 stays open. Settling the language and the bytecode format still takes a captured official bytecode message and the GS2 documentation in the archived websites **[inf]** (`protocol/graphics-movement-bytecode.md`). Preagonal is a lead for how one reimplementation splits source from bytecode, which opcodes it bothers to run, and which behaviours a clean-room VM must not copy from it.
