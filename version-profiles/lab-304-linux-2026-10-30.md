# Lab run: the real 3.04 Linux client on GServer-v2

Date: 2026-10-30

The 3.04 Linux client (the original UPX-packed executable from the installer) was run in a cloud container: i386 libraries, Xvfb with Mesa software GL, and a network namespace with loopback only. `/etc/hosts` in the namespace pointed `<list-host-3x>` at 127.0.0.1, so the signed `license.graal` did not need editing. The servers were GServer-v2 (with `G3D03014` added to `allowedversions.txt`) and the lab listserver, extended to accept the 3.x listserver login. One online session ran for about 5 minutes. A short offline session followed. Tags as elsewhere: **[cap]** seen on the wire or on screen in this run.

## Setup, for repeating it

- Packages (Ubuntu 24.04, i386 multiarch): `libc6`, `libx11-6`, `libxext6`, `libgl1`, `libglx-mesa0`, `libgl1-mesa-dri`, `libglu1-mesa`, `libopenal1`, `libasound2t64`, plus `xvfb`, `xdotool` and `iproute2`. The client ships its own SDL 1.2 and fmod in `lib/`, and `libstdc++` is linked in.
- Run it from the install folder with `LD_LIBRARY_PATH=./lib`, inside the namespace, on an Xvfb display of 1024×768×24 with GLX. It opens at 800×600 and keeps its prefs and `console.log` under `~/.garagegames/graalexe/`.
- In the namespace, bring `lo` up before starting the servers. GServer-v2 needs `G3D03014` in `config/allowedversions.txt`. The lab listserver must accept id 7 in the first plain frame and answer in gen 5.
- The client scans its folders only at startup, so a level copied in later is not found until a restart.
- The UPX stub leaves the running process named `3`, so `pkill graalexe` matches nothing. Stop clients by pid.
- A second client needs its own `HOME` (prefs live under `~/.garagegames`) and its own X display.

## Startup and listserver

- The client runs as shipped. Sound fails to open (no device) and the game carries on. The start window, server list and in-game screens match what the TorqueScript files describe. **[cap]**
- **Listserver login is one frame.** The client sends a single plain zlib frame holding both id 7 (`key`, `G3D30123newmain`) and id 1 (account, password). Static reading suggested a flush between them; the wire shows none. The lab listserver answered in gen 5 (compression byte plus partial XOR, keyed with that key), and the client showed the list and the status line. **[cap]**
- The server list shows only the tabs that have servers. A server name with no prefix appears under Classic. **[cap]**

## Game login

- The first frame is plain zlib (no compression byte, no XOR) and holds four messages: 5 login (type 5, key, `G3D03014`, account, password), 37 `English`, then 34 UPDATEFILE for `bigmap.txt` and `minimap.txt`. GServer-v2 logged it as "New Client (2.22+)", version 3.041. **[cap]**
- Every later frame is gen 5. The server's first reply used bz2 (compression byte 6) and the client decoded it. **[cap]**
- First props message (id 2) after the level arrives: 0 NICKNAME, 18 STATUS, 31 UDPPORT (a random port, as `fixedport` is 0), 33 ADDITFLAGS 0, 52 PLANGUAGE `English`, 75 OSTYPE `linux`, 76 TEXTCODEPAGE 1250. **[cap]**
- Then 34 UPDATEFILE for the player's head and the two default weapon icons, and 23 WANTFILE for the player-list status icons named by server id 180. These come in two batches, which matches the five-request queue limit. **[cap]**
- **No 39 (tampercheck) in the whole session, and no periodic message over TCP.** In five minutes of mostly idle play the client sent only 1, 2, 13, 18 (GServer's movement script), 23 and 34. 2.31 sends 39 about every 3.2 s and 24 about every 5.1 s. The 5.1 s message does exist in 3.04, but it goes over UDP to other players (see the two-player run below), and this session had no other player. **[cap]**

## Movement and animation

- Walking moves 0.5 tiles per 50 ms (10 tiles per second). While moving, the client sends X or Y every 100 ms. When the key is released it sends `idle` about 0.1 to 0.15 s later. **[cap]**
- **Pushing against a wall:** the `push` gani starts about 0.9 s after the player stops against a blocking tile. Releasing the key after 0.6 s did not trigger it. **[cap]**
- **Chat:** the text is drawn above the head in white with a one-pixel blue shadow down and to the right. There is no bubble or box. Tab opens the chat bar along the bottom of the screen. **[cap]**
- Key bindings (Torque `config.cs`): arrows move, A, S and D are the item keys, Q, P and M open windows, T is the microphone, F3 options, F5 load level, F7 player list, F8 server list. **[file]**

## Bushes, lifting, items

- **Sword on a bush:** the client sends 34 UPDATEFILE for `sword.gani`, then 1 BOARDMODIFY (2×2 tiles), then gani `sword`. The `sword` gani lasts 0.25 s before `idle`. The server echoes 7 and adds a dropped item with 22. **[cap]**
- **The dropped item vanished after 8.3 s.** The client sent 13 ITEMDEL for it on its own, without being picked up. **[cap]**
- **Respawn online is the server's job.** GServer-v2 restored the bush with 7 BOARDMODIFY 14.6 s after the cut (its `respawntime` is 15). The client only draws what the server sends, so this lab cannot give the official server's respawn time. **[cap]**
- **Lifting a bush:** 1 BOARDMODIFY at once, gani `lift`, carry sprite 1 after 0.2 s, `carrystill` after 0.3 s, and `carry` while walking. **Throwing** sends only `idle` with carry sprite −1. No 11 THROWCARRIED was sent for a thrown bush. **[cap]**

## Offline

- Offline mode (the Tutorial button) loads `levels/tiledefs/tiledefsOffline.txt`, one line: `picso.png,offlinetutorial,1,0,0`. `picso.png` is a 1024×512 sheet of terrain only (water, sand, grass, rock, snow, ice). It has no bushes, pots or liftable stones, so the tutorial levels have none either. **[file]**
- A test level (`labbush.nw`: grass, with four each of classic bush 2/3/18/19, stone 34/35/50/51 and vase 684/685/700/701 tiles) was loaded offline with F5. The objects draw wrongly (each 16-pixel cell shows a whole small object, and the bushes and stones alternate by position whatever their tile ids), the player walks through them, and the sword does not cut them. The same happened with the offline tiledefs file removed. Loading the GServer world level offline gave the same kind of broken picture. **[cap]**
- So **3.04 has no offline respawn to measure**: offline, the classic cut, lift and break objects do not work at all. Online, the server does the respawn (above). **[cap]**

## Two players: the UDP channel

Two clients (separate prefs folders, one Xvfb display each) logged in to the same level. Both had `noudp = 0`, as shipped for Linux. The decoder is the 2.05 one from `protocol/udp-p2p.md`, unchanged. **[cap]**

- **Same channel as 2.05.** Each datagram is `seq` plus `GCHAR id` plus fields, XORed whole with `recipientId XOR 1`: key 3 to player 2, key 2 to player 3. `seq` counts from 0 per sender and recipient pair. There is no zlib and no length prefix.
- **Id 0, movement:** X×2, Y×2, SPRITE, STATUS (21), CARRYSPRITE (−1), and the first letter of the current gani (`W` walk, `I` idle, `S` sword). It is sent every 100 ms while moving, then once on stopping. The same position also goes to the server over TCP as props.
- **Id 15 with one byte, 9: sent about every 5.1 s to each peer.** This is the message 2.31 sends over TCP as 24 every 5.1 s with the value 9. In 3.04 it goes to peers over UDP and not to the server.
- **Id 22, chat:** the raw text. The same text also went to the server as prop 12 over TCP.
- **Id 26, trigger action:** a mouse click sent `0 0 0` (an NPC id of 0), X×2, Y×2 and the action `leftmouse`. It went over UDP only, with no TCP copy.
- In both two-player runs, one of the two clients stopped sending UDP to its peer after 11 to 20 s, and its later chat went over TCP only. The trigger for this was not traced.
- The other player's name shows under them in blue. While a client window has no focus the name reads `name (paused)`.
