# Lab run: real 5.00r7, 5.12 and 5.24r4 clients on GServer-v2

Date: 2026-10-30

Three real Graal 5 Windows clients were run under Wine 9.0 on Xvfb, against the prebuilt GServer-v2 lab server, in a network namespace with loopback only. The clients were the full 5.00r7 install (with the private folders left out), the original MoleBox-packed 5.12 setup executable, and the MoleBox-packed 5.24r4 executable. A logging proxy between client and server decoded gen 5 in both directions. A second version of the proxy could also rewrite or add server messages.

Tags: **[cap]** means seen on the wire or on screen in this run. **[bin]** means read from the client binary. Times come from the proxy log, which has millisecond timestamps. A tick is 50 ms.

## Setup, for repeating it

- In the namespace, `/etc/hosts` points `loginserver*.graalonline.com` and `listserver*.graalonline.com` at 127.0.0.1. The stock `license/license.graal` (host `loginserver.graalonline.com`, port 14900) then reaches the proxy on 14900, which forwards to GServer on 14901.
  - The 5.00r7 folder came with a `license.graal` that had been edited to point at a private LAN host. The stock file from the 5.12 bundle replaced it.
- GServer-v2 needs the tokens in `config/allowedversions.txt`: `G3D22067` (5.00r7), `G3D14097` (5.12), `G3D15010` (5.24r3/r4), `G3D26090` (5.30r3/5.31r4).
- **Stock gs2lib does not know `G3D15010`.** It treats 5.24 as a pre-2.1 client, so file messages come in the old layout. 5.24 then tries to save PNG data as the file name ("Couldn't open …1.png‰PNG… for writing"). In a lab copy of `libgs2lib.so`, the `G3D26090` table entry was renamed to `G3D15010`. With that copy, 5.24r4 downloads files normally. **[cap]** Since 2026-10-31 the proper fix is `tools/lab-servers/gs2lib-CLVER_5_24.patch`, which gives 5.24 its own slot and leaves `G3D26090` in place. The rule (layout chosen by the server's token table) is in `protocol/file-transfer.md`.
- Wine:
  - Under Wine, 5.00r7 and 5.12 draw through Direct3D 7, and 5.24r4 draws through OpenGL. **[cap]**
  - Setting wined3d's renderer to Vulkan gave a black screen. The default GL renderer works. **[cap]**
  - There is no window manager, so `xdotool windowfocus` on the game window is needed before keys reach it. The client also pauses while unfocused. **[cap]**

## Login mode: why nothing is drawn at first

- **Fact.** The client treats the server it reaches through `license.graal` as the **Login** server. The console says "Loading tile definitions for server Login", and the window title is " L o g i n ".
- **What it hides.** In Login mode the client draws the level tiles, chests and image NPCs, but no characters (neither its own player nor other players) and no default HUD. On the real service, that server is only the backdrop for the scripted server list. **[cap]**
- **Same check in 4.04.** The v4 lab found the same rule in the 4.04 engine. If the current server name starts with "login" (case-insensitive), the draw-layer mask is 0 instead of the full mask.
- **What did not fix it.** None of these changed anything:
  - adding body, head, sword and shield images and ganis locally;
  - a fresh file-name cache;
  - a gani script reply;
  - a curlevel prop for the player itself;
  - removing the colours prop;
  - a different Wine renderer.
- **The fix is S→C 178 (`PLO_SERVERWARP`).** Send it after the login burst. Here it was sent right after S→C 182, with the text `0,Lab Server,127.0.0.1,14900`.
  - The client closes the connection and logs in again with a new key, to the host and port in fields 2 and 3.
  - The second connection is named after field 1. The window title becomes " L a b   S e r v e r " (5.24r4: "Lab Server").
  - On that connection the client draws:
    - the player, with shadow, head, body, sword and shield;
    - other players, with their nicknames;
    - hearts, the A/S/D item boxes, the counters, the AP bar;
    - the native player list window. **[cap]**
- **GServer-v2 and 178.** GServer-v2 sends 178 only when a listserver answers its server-info request, so the lab proxy injected it. The same warp works for 5.31r4 and 6.03r7 (the "Play v5 and v6 clients" lab).
- **Tile definitions after the warp.** The client asks for `tiledefs<servername>.txt`, with the space escaped as `%032`.
- **Implication for a server emulator.** A v5+ client must end up on a server whose name does not start with "login". Otherwise the player never appears.

## Message flow seen in this run

- **Login.** The login frame and the order of the server's login burst are as described in `protocol/v5x-clients.md`. **[cap]**
- **Frame types the client accepts.** The rewriting proxy re-encoded every server frame. With every frame sent as zlib (type 4), the client disconnected after a few frames. It stayed connected once payloads of 55 bytes or less went as type 2 (plain, XOR over up to 12 dwords) and larger ones as zlib. Payloads over 8 KiB went as bz2 (type 6). That 55-byte limit is the one GServer uses. **[cap]**
  - Only the combination was tested. The exact rule the client applies is not known.
- **Movement.**
  - While walking, the client sends a props message (C→S 2) **every tick**. It carries only the coordinate that changed: X2 (prop 78) or Y2 (prop 79). The value is pixels × 2, with the low bit as the sign, so positions go out in whole pixels.
  - The gani change goes in the same message as the first step (`*` walk, then `n`/`o`).
  - 5.24r4 also adds prop 17 (sprite/direction) to gani changes. 5.00r7 and 5.12 do not. **[cap]**
- **Files.**
  - A gani is checked with C→S 34 (UPDATEFILE), or with C→S 23 (WANTFILE) when it is not cached.
  - Then comes C→S 157 (the gani name and a 5-byte checksum). The server answers with S→C 195 (gani name and attribute text, for example `SETBACKTO idle` for `sword`). **[cap]**
  - 5.12 and 5.24r4 fetch `sword.wav` and `lift.wav` from the server with WANTFILE the first time they are needed. 5.00r7 has them locally. **[cap]**
- **Pushing into an object.** While the push pose lasts, the client sends C→S 38 with the text `pushed,0` and the object's position. The first goes about 550 ms after `push` starts, then one every second. **[cap]**
- **Cutting and lifting a bush.**
  - Both send C→S 1 (BOARDMODIFY) with the 2×2 stump tiles. GServer echoes it to everyone as S→C 7. **[cap]**
  - Lifting sets prop 19 (carry sprite) to 1.
  - Throwing sends C→S 11 (no payload) and sets the carry sprite to −1. **[cap]**
- **Respawn is the server's job.** GServer-v2 restored the bush with S→C 7 exactly 15.0 s after the cut, which is its `respawntime = 15`. The client does not put tiles back by itself online. The respawn time a real 5.x server used was not observed. **[cap]**
- **Periodic messages.** C→S 24 about every 5 s, and S→C 42 (world time) every 5 s. **[cap]**
- **Clientside scripts.** NPC scripts arrive as source text in S→C 3 (with `§` for line breaks), not as bytecode. Clientside NPC scripts were only tried while the clients were still in Login mode, so whether they run was not settled. **[cap]**

## Timings

All three builds gave the same numbers.

| action | 5.00r7 | 5.12 | 5.24r4 |
|---|---|---|---|
| walk | 0.5 tile (8 px) per tick, 41 updates in 2.0 s | same | same |
| first step after key down | about 1 tick (16–54 ms) | same | same |
| key released → `idle` | next tick (38 ms) | same | same |
| last refused step → `push` | 908 ms (18 ticks) | 902 ms | 902 ms |
| `sword` → `idle` | 248 ms (5 ticks) | 243 ms | 246 ms |
| `lift` → `carrystill` | 304 ms (6 ticks) | not run (bush already cut) | 299 ms |
| carry walk | 0.5 tile per tick, `carry` | — | same |
| hidden walk (D while carrying) | — | — | 35 px in 22 ticks = 0.1 tile per tick, `hidden` / `hiddenstill` |
| blocked against a corner | small x nudges of 1–2 px per tick toward the gap | — | — |

These match the 2.05 timings in `client-internals/player-mannerisms-live.md`: push on the 18th blocked tick, sword 5 ticks, lift 6 ticks, hidden 0.1 tile per tick. **[cap]**

## How it looks

- **Chat text** (another player's chat, seen from 5.12):
  - It is drawn above the head, centred, as white bold sans-serif text with a blue drop shadow down and to the right.
  - The shadow colour is mostly RGB (88, 88, 255), with some pure (0, 0, 255).
  - There is **no bubble box**. **[cap]**
  - The nickname is drawn the same way under the player.
  - A player whose window is inactive shows as `name (paused)`.
  - The client's own nickname is not drawn under its own player.
  - Shot: `client-internals/mannerisms-shots/v5-512-chat-text-zoom.png`.
- **Chat input needs the server.** When it decides whether keyboard input belongs to a text field, the engine looks for a GUI control named `ChatBar`. **[bin]**
  - On a bare GServer-v2 there is no such control. Typing, Tab and Enter do nothing, and no chat message is sent. **[cap]**
  - The chat bar is therefore part of the server's scripted GUI, not of the engine. The chat text above was injected as prop 12 through the proxy.
- **Carrying and hiding:**
  - A carried bush is drawn over the top of the head. Facing down, the face stays visible below it (`v5-500r7-carry-down.png`).
  - In `hiddenstill`/`hidden` only the bush is drawn, at the player's feet, and the player is not drawn at all (`v5-524-hold-hide-hidden.png`). **[cap]**
- **HUD:**
  - 5.00r7 and 5.12 label the item boxes A, S and D and print the sword level next to the sword.
  - 5.24r4 draws the same boxes without the letters and without the level number (`v5-hud-512-vs-524.png`).
  - **Possibly Wine-specific.** 5.24r4 is the one build that draws through OpenGL here. It may simply not be drawing that text under Wine, so confirm this on real Windows before using it in a profile. **[cap]**
- **Player list.** The player list is a native Windows window, titled "Players: N online", with tabs and the groups Staff, Buddies, Guild, Normal, Ignore and Offline. 5.00r7 and 5.12 opened it at login. 5.24r4 did not. **[cap]**
- **Tile graphics.**
  - In Login mode the level used one tile set.
  - After the warp, 5.00r7 used its newer default tile graphics. Bushes became the red-and-white flower bushes, and stones became pale green blocks (`v5-500r7-after-warp.png`).
  - The client asks for `tiledefs<servername>.txt` after the warp, so the change of art probably comes from tile definitions chosen per server name. **[cap]** for the request, the cause is an inference.

## Not covered here

- Pots and stones: the test level has none. The respawn rule above (the server restores the tiles after its `respawntime`) applies to them as well; their per-object timing was not measured.
- 5.30r3 and 5.31r4 were run by the "Play v5 and v6 clients" lab, not here.
