# How the 3D server takes bad input: handshakes, malformed packets, floods, reconnect storms, and out-of-range positions (T3D-142/143/144/145/146)

Date: 2026-11-26. Lab: a synthetic proto-24 client (the T3D-164 client, in fuzz modes) as
the attacker against seihai-gserver main (5cd9c15) on the loopback, with a real 5.12 under
Wine/Mesa watching where the row needs one. Behaviour only; the fuzz tooling stays in the lab
kit, off every PR. **[lab]**

This answers five robustness rows against our own clean-room gserver. The headline: the
server never crashed, panicked or restarted in any case; handshake garbage, malformed packets,
a position flood and a reconnect storm are all handled cleanly with no leak, and the one real
gap is that out-of-range client positions are forwarded unsanitized, which has a small, local
fix.

## T3D-144 — garbage and unsupported handshakes (19 cases): clean

No real client needed. After each case a fresh socket completed a proper handshake as a
liveness check. The server survived all 19 and every liveness handshake got a connect-accept.

- **Clean rejects** (connect-reject with the client's own reason string): protocol 99 / 0 /
  0xffffffff and a minimum protocol above the current one → `CHR_PROTOCOL`; a wrong game name
  → `CHR_GAME`; a wrong connection class → `CHR_INVALID`; argc 0 and argc 0xffffffff with no
  args → `CR_INVALID_ARGS`.
- **Silently dropped** (no reply, no log line): a truncated challenge request, an empty
  datagram, 64 and 1400 random bytes, a connect request with no prior challenge, a bad digest
  (random 16 bytes after a real challenge), truncated connect requests, a connect-accept sent
  to the server, and a data packet with no link.
- **Logged and held**: a connect request for an account with no matching TCP login →
  "asked for a 3D link … but no TCP login … matches it (yet)", no reply, as designed.

The only remark is that the silent drops (a bad digest especially) leave no trace in the log,
which is fine for robustness but invisible to an operator; a rate-limited debug line would
help if wanted. No correctness gap.

## T3D-142 — malformed 3D UDP updates (8 cases): clean except one downlink wedge

A real 5.12 (pc:1) watched while the synthetic client moved its cube normally and sent one
malformed data packet every 5 s in place of a normal one. The server survived all eight and
kept reading the client's normal packets after each (positions applied to the end). The real
5.12 was **unaffected** — the cube kept moving through all eight and left normally on quit.

- Object update with extra sections + junk bits, or sections claimed with no data → "could
  not read the client's game section: … runs past the packet's N bits", packet skipped.
- A guaranteed event claiming 16000 bits with 30 present → "could not read the client's
  events: Short(OutOfBits)", skipped.
- A packet truncated after the header → dropped silently.
- An unguaranteed event with an unknown class id → "event ignored: (unknown class)".
- A RemoteCommandEvent with 31 int args and no name → ignored, no log line.
- A sequence jumped +200 (more than 31 ahead) → dropped silently, by design.
- A forged ack header (ack-byte count 7, the max being 4, with a highest-ack 300 ahead of
  anything sent) → dropped whole (an over-length ack count or an out-of-window highest-ack is
  rejected at the header). No state change, correct behaviour.

No correctness gap: every malformed class is skipped or dropped, and the server keeps reading
the client's normal packets after each. (An earlier run read a "send window full" wedge as a
server gap; on checking the exact bytes it was the *test client's* own sequence-widening bug —
it compared the server's 9-bit sequences raw and stopped acking once the server's sequence
wrapped past 511, so the server's "acks nothing new" response was correct. The server has no
bug here; the finding was withdrawn.)

## T3D-143 — a position-update flood (500 Hz): stable, no throttle, negligible load

A real 5.12 (pc:1) watched while the synthetic client, after taking control, sent a full data
packet with a fresh section-4 transform at **500 Hz** for 20 s (9,985 packets, ~25× its normal
rate and ~200× the 5.12's 2–3 Hz), then returned to normal.

The server stayed stable and applied the updates (2,755 distinct position lines; identical
consecutive positions are folded in the trace), with no warning, throttle line, drop or
"window full", and the link held to quit. Load was small: the process's lifetime-average CPU
rose only from 0.5 % to 1.1 % over the flood (a few percent of one core at most) and RSS
peaked at 7.3 MB. **The server does not rate-limit or coalesce 3D client packets — every one
is processed** — which is fine at this load; a per-link cap or coalescing would only matter
under much heavier abuse (many clients flooding at once, untested). The real 5.12 was
unaffected: the cube moved smoothly through the flood with no desync or stall, because its view
follows the server's own ~20 Hz downlink whatever the uplink rate.

## T3D-145 — a reconnect storm: stable, clean teardown, no leak

30 full connect cycles on one account (TCP login → UDP link → mission start → control object),
back to back over ~50 s (odd cycles hard-killed at 1.5 s mid-session, even cycles exiting at
2 s), while two half-open links were held for 45 s: one that completed the UDP link then went
silent on UDP with TCP open, and one TCP-login-only. A real 5.12 (pc:1) watched.

The server stayed **stable and clean**:

- The 30 cycles gave 30 "linked" / 30 "link closed" / 30 "left (Connection reset by peer)", and
  **every link was cleaned up** ("object deleted on N other clients"). Re-login on the same
  account straight after a hard kill worked every time, with no double-login refusal.
- The silent-UDP half-open link timed out on the server's own clock ("link closed (The 3D
  connection timed out)") and its object was deleted, while its TCP session stayed until the
  client closed it. The TCP-login-only client was an ordinary 2D player (shown to the 3D
  clients as `G2DPlayer_<acct>`) with no 3D side effects.
- **No leak**: sampled every second, the process RSS went 5.1 → 8.4 → 8.5 MB steady, threads
  9 → 12 → 9, open fds 12 → 16 → 12 — all back to baseline after the storm. No panic, no error
  lines.
- The real 5.12 was unaffected and left with **no stale ghosts**: 30 `G3DPlayer_<acct>` creates
  matched the 30 deletes, the transient extra cubes appeared only during the storm, and after
  it only the 5.12's own cube remained.

## T3D-146 — out-of-range control-object positions: unsanitized, and they poison others

A real 5.12 (pc:1) watched while the synthetic client, after taking its control object,
reported 10 s each of a normal position, then NaN x, +Inf x, 1e30 x,
(−3e38, −3e38, 3e38), then a normal position again — in both the game-section position and
the section-4 transform update.

The server survived and the links held, **but it does not sanitize the value.** It accepts
every one as the player's position and logs it verbatim
(`… control object: … at NaN,3.00,1.00`, `… at inf,…`, `… at 1e30…`, `… at -3e38,-3e38,3e38`),
with no clamp, drop or warning. The only finiteness check in the code is on the script /
g3dpos route, not on the client's own game-section state.

The real 5.12 watching survived (no crash, no console error, linked until quit) but was
**affected on screen**: the synthetic client's cube is drawn normally in the first phase, then
disappears from the NaN phase onward, and — crucially — **does not come back after the
synthetic client returns to a valid position.** So one NaN, Inf or huge coordinate poisons the
other client's copy of that player for the rest of the session, even after good positions
resume. The likeliest cause is that the server forwards the bad transform and the 5.12's
interpolation never recovers from NaN (the forwarded bytes were not captured; a capture can
confirm it). A re-run with a corrected test client (ruling out any client-side confound)
reproduced it exactly. A local fix: reject or clamp non-finite and out-of-world positions from
the client's game section — the same `is_finite` check the script route already has, plus a
world/terrain-size bound — and keep the last good transform. The gserver work has taken this
fix (a position, rotation or scale that is non-finite or lies more than 100000 units out is set
aside and the last good one kept).

## Verdict

Our gserver is **crash-robust** on every input class tried: bad handshakes, malformed packets,
a 500 Hz position flood, a 30-cycle reconnect storm with half-open links, and out-of-range
positions all leave it running and still serving other clients. Garbage handshakes (T3D-144),
malformed packets (T3D-142), the flood (T3D-143) and the reconnect storm (T3D-145) are all
handled cleanly with no state gap and no resource leak — the server keeps serving valid
traffic, tears every link down, and other clients are unaffected with no stale ghosts.

**One real gap remains: non-finite or astronomically large client positions are forwarded
unsanitized** (T3D-146) and poison other clients' view of that player for the rest of the
session. It is reported to the gserver work with the suggested `is_finite` + world-bound
check (fixed there: a position/rotation/scale that isn't finite or lies more than 100000 units
out is set aside and the last good one kept). It is not a crash and does not reach beyond the
one world, but it lets one client degrade others' session, so it matters for a server meant to
face untrusted clients.
