# 5.12 content fuzzing: `.3ds`, `.dts`, `.dif`, PNG (2026-11-25)

Lab: the real 5.12 client in a VM, served one mutated level file at a time
from our own Seihai gserver (never a third-party server). Each world carried
a single mutated file under a fresh name; runs were unattended with a VM
snapshot restore after any run that lost the client. Behaviour only; crash
addresses, per-run files and screenshots stay in the lab share. Board row:
T3D-038. **[lab][cap]**

The theme across all four formats: a malformed file damages only the one
client that loads it. Nothing reached the gserver or other players in any
case.

## `.3ds`

| Mutation | Result |
| --- | --- |
| Truncated by any amount | Client vanishes — no window, no error box |
| Face count 12 → 65535 | Access violation inside `GRAAL3DENGINE.DLL` |
| First face index 0 → 65534 | Crash inside `opengl32.dll` (a bad index reached the GL driver) |
| Vertex count → 65535 | Drew normally |
| Version → 99 | Drew normally |
| Short face-material sub-chunk | Drew normally |

So the `.3ds` reader does not bound-check the face count or the face index
before handing them on: a large face count faults in the engine itself, and
a large face index is passed through to OpenGL and faults in the driver.
Vertex count, version and a short material sub-chunk are tolerated.

## `.dts`

| Mutation | Result |
| --- | --- |
| Truncated to 30%, or total-size word made huge | Crash (write to a bad or null address) |
| Truncated to 70% | Vanishes silently |
| `start16` → 65535 | Drew nothing; the link held |
| Version → 0 | Drew nothing; the link held |

Consistent with the earlier `.dts` finding that the reader trusts the
version word (`torque/live-512-shapes-2026-11-25.md`): a plausible-looking
but wrong body crashes or draws nothing rather than being rejected. A badly
truncated file or an inflated total-size word crashes; a milder truncation
loses the client silently; `start16`/version out of range draws nothing but
keeps the connection.

## PNG (textures)

| Mutation | Result |
| --- | --- |
| IHDR set to 30000 × 30000 | Crash (huge allocation or a null read) |
| Flipped CRC | Drew wrong or white; no crash |
| 50% truncation | Drew wrong or white; no crash |
| GIF signature on a `.png` | Drew wrong or white; no crash |

The client does **not** check the PNG CRC — a flipped CRC draws without
complaint. Oversized IHDR dimensions crash it (unchecked allocation / null
read). Truncation and a wrong signature degrade the image but do not crash.

## `.dif`

`.dif` never crashed. Truncated to 10%, 50% or 95%, or version set to 0 or
45, the link always held and the client stayed up. Of the four formats the
`.dif` reader is the most robust to malformed input.

## What this means

- The client is the trust boundary: a malformed content file crashes or
  degrades only that one client, never the server or other players.
- Unchecked numeric fields that crash: `.3ds` face count and face index,
  `.dts` truncation / total-size word, PNG IHDR dimensions.
- Tolerated without crashing: `.3ds` vertex count / version / short material
  chunk, `.dts` `start16` / version (draw nothing), PNG CRC / truncation /
  wrong signature (draw wrong), all `.dif` mutations tried.
- A server that serves the real client must therefore produce well-formed
  `.3ds`/`.dts`/PNG; the client will not defend itself against these fields.

## 4.04r2 login player shape (`.dts`, protocol 19) — tier 2a

A separate run (4.04r2 under Wine on Mesa, gserver #154 @ ca00d9a6) fuzzed
`tgeplayershape.dts` — the `PlayerData` shape the client loads in Phase 1 at
login — with 21 runs (one baseline + 20 mutations of the v24 octahedron).

**16 of the 20 malformed files crash the client at login:**

- truncated to 25%, 50%, 75% or 95%;
- the 32-bit buffer-size word set to `0x7FFFFFFF` or `0`;
- the 16-bit section start pushed past the buffer;
- the node, object or subshape count set to `0x7FFFFFFF` or `-1` (all six);
- unterminated name strings;
- three seeds of 0.5% bit flips.

Every crash looks the same: the console stops at "Phase 1: Download
Datablocks", an access-violation box names the client's 3D engine DLL (reads
and writes), and the server ends the link ~30 s later with "The 3D
connection timed out". Nothing reaches the server or other clients.

**4 cases survive** and reach the control object: the baseline, the 8-bit
section start past the buffer, the 16- and 8-bit starts swapped, and the last
24 bytes (material-list tail) set to `0xFF`.

So **protocol 19 has no tolerance for a bad login player shape**: any
structural damage the `.dts` loader reads kills the client during Phase 1.
This reinforces the tier-1 finding that `.3ds` and `.dts` are the dangerous
types. A server-side `.dts` sanity check before sending (buffer size, section
starts and node/object/subshape counts all within the file) would cover all
16 crash cases.

## 5.12 terrain content (`heights.info` + textures, pushed) — tier 2b

Real 5.12 under Wine on Mesa llvmpipe, gserver #154 @ ca00d9a6 with
`graal3dpushterrain`, world `g2t`, cache cleared each run; 15 runs mutating
`heights.info` or the first terrain texture (`g3d_water.png`).

**Two cases crash the client** (access violation, null read, before Phase 3
— same class as the tier-1 giant-IHDR object texture):

- a terrain-texture PNG whose header claims 30000 × 30000;
- a terrain-texture PNG whose header claims 65536 × 1.

**Everything else survives, degrading sensibly:**

- `heights.info` empty or random bytes: no texture requests, ground white.
- One name only: one texture fetched.
- A name the server lacks: "not found", and the start-up check warns.
- A 4004-character name: that layer is skipped, the others draw.
- Texture PNG cut at 50%: that layer draws as black-and-grey stripes.
- Texture PNG 0 bytes, or a GIF signature: that layer is skipped.
- Valid 1×1 and 256×256 grey PNGs: fine.

**`heights.info` parsing is strictly one name per line.** With four names on
one line, 5.12 asks the server for the whole line as a single file name —
the format is line-delimited, not whitespace-delimited. So the terrain
texture list the client reads is one filename per line, and a stray space in
a name becomes part of the requested filename.

The oversized-dimension crash is the same unchecked-allocation / null-read
class as the object-texture IHDR crash in the 5.12 section above: a terrain
texture is no safer than a shape texture on that field.
