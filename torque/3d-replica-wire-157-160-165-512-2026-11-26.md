# Replica wire basis: packet inventory, UDP framing, ghost lifecycle, class table, asset envelope (T3D-157, T3D-158, T3D-159, T3D-160, T3D-165)

Date: 2026-11-26. Lab: one instrumented real 5.12 session (G3D14097) in a Windows
10 VM, loopback, against seihai-gserver main (8800c2b) with a lab-only wire log
(server and client share one guest, so nothing reaches a NIC; every decoded gen5
TCP body and every raw UDP datagram both ways was logged with wire sizes, ~1,215
records). The world exercised join, a file-fetch of each asset type, player.chat,
a weapon3d `play`/`g3dhide`/`g3dshow`/`g3dpos`, a `g3dworld` switch to a second
world and back, and a second 5.12 joined so the capture also holds two parallel
sessions and their mutual ghosts. Behaviour only; no addresses; captures stay in
the lab kit. **[lab][cap]**

These five rows are the reimplementation basis for a replica client — the wire it
must speak. Builds on [the engine-DLL interface + net-event note](3d-engine-dll-interface-and-events-2026-11-26.md)
(T3D-097, the static class/event table) and [the session-lifecycle note](3d-session-lifecycle-420r6-2026-11-26.md)
(T3D-130, entry/warp), which this confirms and extends on the live wire.

## T3D-157 — the full packet inventory a session uses

**TCP, client→server (gen5 ids):** 2 PLAYERPROPS (incl. the chat prop), 23
WANTFILE, 24 SHOWIMG-id, 34 UPDATEFILE, 37 LANGUAGE, 46 ENTERLEVEL-id, 152 and
154 (GServer-v2 names these REQUESTTEXT/SENDTEXT; our server logs them "not
handled"), 157 UPDATEGANI.

**TCP, server→client:** 6 LEVELNAME, 8 OTHERPLPROPS, 9 PLAYERPROPS, 10 ISLEADER,
14 PLAYERWARP, 25 SIGNATURE, 30 FILESENDFAILED, 32 SHOWIMG, 33 NPCWEAPONADD, 39
LEVELMODTIME, 42 NEWWORLDTIME (the 5 s heartbeat, 41×), 43 DEFAULTWEAPON, 45
FILEUPTODATE, 68 LARGEFILESTART, 84 LARGEFILESIZE, 100 RAWDATA, 101 BOARDPACKET
(inside RAWDATA), 102 FILE (inside RAWDATA), 156 SETACTIVELEVEL, 168 ONLINEMODE,
178 SERVERWARP, 180 STATUSLIST, 190 SERVERLISTCONNECTED.

**UDP out-of-band** (first byte, bit 0 = 0): client challenge-request and
connect-request; server challenge-response, accept, and disconnect.

**UDP data (the 3D net-event layer):** C→S `RemoteCommandEvent`
(MissionStartPhase1Ack/2Ack), `BigDataStartEvent` + `BigDataChunkEvent`,
`TerrainRequestUpdatesEvent` (terrain worlds), plus the own-object/control state
in every data packet, and acks. S→C the ghost-always/BigData/TerrainChunk/
NetString/RemoteCommand/ConnectionMessage events of T3D-097.

**Deltas from the prior static baseline — the things a replica would otherwise
miss:**
- Six client→server TCP ids were **not** on the baseline: 24, 37, 46, 152, 154,
  157. (152/154 are the REQUESTTEXT/SENDTEXT pair.)
- **5.12 sends its `triggerserver` script text over the UDP 3D link as
  BigData events, not over TCP** (the server logs "trigger ignored"); so a replica
  server reads client triggers off the 3D link, not the 2D channel.
- **Chat is only the 2D PLAYERPROPS chat prop** out (and OTHERPLPROPS to the other
  player); nothing chat-like travels on UDP.
- **Keepalive is NEWWORLDTIME on TCP**; on UDP the server never pings (all
  outbound are data), and the client answers each data packet with a 5-byte ack.
- The client **sent no UDP Disconnect**; a TCP close (a kill) is what made the
  server emit the out-of-band disconnect.
- `RequestReloadEvent` — one of the two client→server 3D events T3D-097 predicted
  — was **never seen** in a normal session.

## T3D-158 — UDP framing

TGE NetConnection notify style, confirmed on the wire. **Out-of-band** packets
have bit 0 = 0 and a one-byte type (challenge/connect/accept/disconnect).
**Data** packets are: flag 1 | connect-sequence bit | **9-bit sequence** | **9-bit
highest ack** | **2-bit packet type** (0 data, 1 ping, 2 ack) | 3-bit ack-byte
count | ack mask; data packets then add two rate flags. Observed: client ~229
data packets (19–97 B) + ~365 acks (5 B, one mask byte); server ~364 data (6–392
B, cap ~450), no pings. Sequences run 1..192 consecutively per side (one or two
non-consecutive steps per stream), no 512-wrap seen. **No packet fragmentation** —
anything large is chunked at the event layer (`BigDataStart`+`BigDataChunk` for
script text and "events" lines; `TerrainChunkEvent` for terrain). So a replica
frames with a 9-bit seq/ack notify header and never fragments; it splits large
payloads into events instead.

## T3D-159 — ghost lifecycle

Indexes are assigned **from 0 in creation order** (Sun 0, Sky 1, world objects,
own `G3DPlayer`, other players, Camera). The ghost section per packet is: flag,
**4-bit index width** (the bit-length of the highest index in *this* packet, not a
fixed int12), then per entry: flag 1 | index | kill flag | if not killed: 12-bit
class id + 14-bit payload length + payload. **Create and update share the form** —
a create carries the full mask, an update only the dirty sections; **a delete is
the index with the kill flag and no body**. Each entry is tracked against the
packet notify, so lost creates/updates/deletes are re-sent. **An index is freed
only after its delete is acked, then reused** (a hidden-then-shown cube came back
at the same index; a world switch deleted 0–3 and re-created the second world on
0–3, then the first world again). The own object and Camera **keep their indexes
across world switches**. (The per-entry layout is from seihai-gserver's writer;
the behaviour is from the capture.)

## T3D-160 — the class table at join

Arrives in the **connect-accept** out-of-band packet (276 B). **19 entries, not
~28:**
- object classes (type 0), ids 0–9: Camera, DynamicGrass, DynamicGrassReplicator,
  DynamicShapeReplicator, GameObject, Sky, Sun, TerrainBlock, WaterBlock,
  fxSunLight;
- event classes (type 1), ids 0–8: BigDataChunkEvent, BigDataStartEvent,
  ConnectionMessageEvent, GhostAlwaysObjectEvent, NetStringEvent,
  RemoteCommandEvent, RequestReloadEvent, TerrainChunkEvent,
  TerrainRequestUpdatesEvent;
- then `u32` protocol 24.

Each entry is `flag | int12 type | int12 server id | Huffman string`. 5.12
accepts it and ghosts by these ids, binding **by name** — so class numbering is
whatever the server sends at join. (This is not proof 5.12 has no built-in list
behind the names; the ~28 figure from the static read is a fuller server's table,
while this server sends only the 19 classes this world uses.) For a replica: ship
the class *implementations* and resolve the wire ids from this name table at join;
a replica server may send any subset its world needs.

## T3D-165 — fetched assets vs the raw file

`.3ds`, `.png` (sky faces + a texture, asked and answered by **bare name, no
extension**), `.wav` (11068 B) and `.ttf` (arial.ttf, 69020 B) were
**byte-identical to the on-disk files once the gen5 frame is decoded**. Each asset
goes as `PLO_RAWDATA(length)` then `PLO_FILE`: GInt5 mod-time, length-prefixed
name, the file bytes, a trailing newline. The `.ttf` (69020 B) came as
`LARGEFILESTART` + `LARGEFILESIZE` + three `PLO_FILE` pieces (32000 + 32000 +
5020) that concatenate exactly, then a `LARGEFILEEND` — the full order per session
is START+SIZE, three FILE pieces, END, matching the server's writer. (An earlier
read of this capture reported the END missing; that was a parser artifact — two
5.12 sessions requested `arial.ttf` in the same millisecond and their log lines
interleaved, affecting 16 of ~1,215 lines; the `LARGEFILEEND` is present.) On the
wire
the gen5 frames are **compressed and encrypted** (an 8416-B body went out as 253
B), but there is **no file-level wrapping, no per-file compression, and no name
mangling beyond the bare-name request**. So a replica asset loader parses the raw
standard formats directly once it has undone the gen5 transport frame.

## For a replica

- **Transport:** a 9-bit seq/ack TGE-notify UDP header (T3D-158); the gen5
  TCP frame (compressed+encrypted) for the 2D channel and files (T3D-165).
- **Ghosts:** indexes from 0 in creation order, per-packet 4-bit index width,
  create=full mask / update=dirty / delete=kill-bit, index reuse after delete-ack
  (T3D-159).
- **Classes:** read the connect-accept name table and bind by name; ship the class
  implementations (T3D-160).
- **Must-haves the baseline missed:** client triggers arrive as UDP BigData, not
  TCP; chat is the 2D chat prop; keepalive is TCP NEWWORLDTIME with per-packet UDP
  acks; the client never sends a UDP Disconnect (T3D-157).
- Assets are the raw formats under the gen5 frame — no extra envelope (T3D-165).
