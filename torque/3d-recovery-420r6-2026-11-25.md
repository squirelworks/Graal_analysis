# How the 3D client recovers from partial or bad data mid-session (T3D-108, Linux 4.20r6)

Date: 2026-11-25. Loopback lab of the Linux 4.20r6 client (5.12-class, protocol 24) against our own 3D lab server, 2D leg through `gen5probe.py` (decode/drop/inject), 3D leg through a UDP relay (runs `rec420-*`; no movement input). Linux 4.20r6 is 3D-equal to Windows 4.20r8 ([T3D-004](3d-engines-5007-512-and-403-411-2026-11-25.md)). Board row: [T3D-108](3d-capability-board.tsv). Builds on [T3D-027](3d-link-drop-420r6-2026-11-25.md) (link drop) and [T3D-060](3d-2d-level-packets-420r6-2026-11-25.md) (2D content inert in 3D).

## Result **[lab]**

| Case | Driven? | Client alive? | Link | Recovery | Console |
| --- | --- | --- | --- | --- | --- |
| Truncated download | yes | yes | kept | none (no re-request) | file reported "done" at a wrong tiny size; no error |
| Update for an unknown object **instance** (2D) | yes (2D side) | yes | kept | n/a | silently ignored; no error |
| Dropped terrain/scene chunk | no — server sends no terrain | — | — | — | — |
| Server restart mid-session | yes | yes | dropped | none (no auto-reconnect) | "Issuing Disconnect packet.", back to login |

The client is **fail-soft, not self-healing**: bad or partial data is swallowed quietly and a lost server sends it back to login, but in no case does it crash, hang, or recover on its own.

## Truncated download

Files arrive inside `PLO_RAWDATA` (100) wrappers (the inner `PLO_FILE` 102 is opaque to the proxy). Dropping the `PLO_RAWDATA` frame as the download burst began gave the client each file's header without its announced bytes.

- The client reported each file **"done" but at the wrong size** (e.g. `sky_fr (size: 5)`, `redcube.3ds (size: 8)` instead of 361 / 505 bytes) — it treats the truncated data as complete. **No length or checksum re-validation** on this path.
- Shapes with the corrupt `.3ds` **did not draw** (only sky and ground showed), but the engine didn't choke on the bad geometry.
- It **did not re-request, hang, time out, or crash**, and stayed fully connected through mission start to Phase 2, heartbeats intact.
- **A later complete send does not recover it**: the client never re-asks, so a re-sent copy is never fetched. Recovery needs a fresh reference or a reconnect.

## Update for an unknown object instance

Injected into a live 3D session: 2D property/move packets addressed to ids the client was never told to create — `PLO_NPCPROPS` for NPC ids 9999 and 12345 (one with an image name), `PLO_BADDYPROPS` for baddy 200, `PLO_OTHERPLPROPS` for player 4242.

- All four were delivered; the client **ignored every one** — no stub object, no reaction, **no image request** for the unknown NPC's image, no error, no disconnect. Extends [T3D-060](3d-2d-level-packets-420r6-2026-11-25.md) (2D content inert in 3D) to updates for a known 2D class but an unknown instance.
- **Contrast with [T3D-085](3d-particles-512-vs-404r2-2026-11-25.md):** an unknown *class* in a ghost drops the link; an unknown *instance* of a known 2D class is just ignored.
- **Not tested:** the 3D-side version (a UDP control-object/ghost update for an unknown 3D ghost id) couldn't be injected — the 3D UDP channel is the encrypted Torque bitstream, which passes through the relay without decode/inject. Only the 2D path was exercised. **[not run]**

## Dropped terrain/scene chunk

**Not drivable on this route.** `TerrainBlock` / `TerrainChunkEvent` are in the client's class table, but our gserver never emits terrain — it sends Sun, Sky, GameObjects, the Camera and the control object, no terrain or scene-chunk event (consistent with the g3d175 notes that TerrainBlock/movetype aren't sent). There is no terrain stream to withhold. Testing this needs the server extended to send terrain, out of scope here. **[not run — no such data on this route]**

## Server restart mid-session

From a known-good connected session, the gserver was killed at ~38 s and a fresh one started on the same port ~10 s later (same world).

- The client noticed **immediately**: the server's TCP closed (FIN at 38.1 s) and the client logged "Issuing Disconnect packet." in the same instant and sent its own FIN — same as the [T3D-027](3d-link-drop-420r6-2026-11-25.md) server-closes-TCP case (reaction in ~0 s, not a timeout).
- It returned to the **login screen** ("You have been disconnected from the game server").
- When the server came back up and was listening, the client **did not reconnect**: no new TCP SYN, no new login. It sat at the login screen for the rest of the run.
- The process/window stayed up — no crash, no hang.

**So:** a server restart is handled exactly like a dropped link — instant notice, back to login, **no auto-reconnect** even though the server is listening again. The user would have to press Start again.

## For a server

- **A truncated or corrupt file is not detected by the client** — it caches it as "done" and the asset is silently blank; the client never re-asks. The server must deliver each file whole (and, for an update, change the file so the client re-fetches), because the client won't self-correct a bad download within the session.
- **Unknown 2D instance updates are harmless** (ignored) — but also do nothing in 3D.
- **There is no auto-reconnect.** After any link loss or server restart the client stops at login; a server can't pull it back, only the user restarting the session will.
