# Graal3DEngine.dll in Windows 4.2.0.8

Date: 2026-11-07. Static read of `Graal3DEngine.dll` from the unpacked 4.2.0.8 set. Nothing was run. Tags: **[bin]**.

This is the third program. On load it registers itself as the host for drawing, text, tiles, panels, clipboard, the 2D matrix and the 3D queries, then calls `graal_engineInitialize`. The launcher afterwards takes back Flash, the external windows and the login hooks (`torque/4208-launcher.md`). The packet-logger upload described in `protocol/v4x-clients.md` and `torque/wire-by-build.md` did not include this DLL; this read is of the DLL itself. **[bin]**

## What GameObject is

`GameObject` is registered under that name. Its constructor calls the constructor of the class registered as `SceneObject`, then installs `GameObject`'s own virtual table and builds a property table. Casts between the two types succeed in both directions, which is the same relationship the RTTI records. A script reaches the object through `TGraalVar` properties: each name is a property with a getter and, for some names, a setter. **[bin]**

What a script can do, from that table: **[bin]**

- Appearance and identity: `shape`, `shapebox`, `scaledshapebox`, `shadow`, `nickname`, `nickcolor`, `alpha`, `hideimg`, `hideimgs`, `findimg`.
- Motion and collision: `velocity`, `movetype`, `solid`, `collision`, `checkCollision`, `checkCollisionByBox`, `clipPolygons`, `getdropz`.
- Terrain and liquid: `showterrain`, `liquidtype`, `liquidheight`, `watercoverage`.
- Mounting: `mountObject`, `unmount`, `unmountObject`, `isMounted`, `attachedtoobject`, and the get-mount and get-mounted queries (`getMountPosition`, `getMountTransform`, `getObjectMount`, `getMountedObject`, `getMountedObjectCount`, `getNodePosition`, `getNodeTransform`).
- Interior queries: `isInInterior`, `getInteriorObject`.
- Control: `getControllingObject`, `getControllingClient`, `iseditorobject`, `setDirection`.

`onRemove` is an event name on the same object. The decompile shows the names and that each has a getter or a setter. It does not show the body of every setter. One body that is visible from the 2D side is `shape`: assigning it is what creates the 3D object (`torque/4208-engine.md`). **[bin]**

`ShapeBase` does not occur. Neither does a Torque `Player` class. `SimObject` is still here, including `deleteObject`. `GameConnection` and `TerrainBlock` are here. There is no `.dso` and no TorqueScript compiler string. That matches the era-B claim in `torque/study-torque-clients.md` that 4.20 has Graal's `GameObject` layer rather than 4.04r2's stock `Player`. **[bin]**

## The login steps

`onGraal3DLoginStep` is one script event, fired with the current step number. The two named phases come first. **[bin]**

Phase 1 logs "Phase 1: Download Ghost Objects", stores step 2, fires the event with that step, and sends `MissionStartPhase1Ack` on the connection. The decompile of this function does not show a file being read or a ghost being constructed. The work visible here is the event and the ack. **[bin]**

Phase 2 logs "Phase 2: Mission Lighting" and stores step 3. It fires the event only when a lighting call returns true. Again this function does not show a mission file being loaded. **[bin]**

The same event continues after those two phases. "Mission lighting done" stores step 4, fires the event, and sends `MissionStartPhase2Ack`. "Initial Control Object" stores step 5 and fires the event. If the step is still 5 and no file download is in progress, the step becomes 6, `GUIContainer3D` is cast to a `GuiControl` and installed with `GuiCanvas::setContentControl`, and the event fires once more. **[bin]**

## What a terrain chunk is

Sending a chunk fills a stream from one square of the terrain block, compresses that stream, and posts an event object. The event records the two indices and a third integer taken from the block, and the log line is "sending terrain chunk" with those two indices. The decompile does not show the byte layout of the compressed block. **[bin]**

The height query, when a wrap flag on the block is clear, rejects an x or y outside 0..255 and otherwise samples a grid of short pairs. That is the in-memory lookup. It is not a description of the chunk file. **[bin]**

## How the three host calls are used

`graal_setCreateGraal3DGameObject` stores the 3D DLL's creator. The engine calls it when a show-image has no 3D object yet and a shape is being set; an empty slot returns 0 and the assignment stops. The creator allocates a `GameObject`, constructs it with the name it was given, and returns it. **[bin]**

`graal_setGetGraal3DTerrainHeight` stores a callback the engine can call with four arguments. The wrapper returns 0 when no host is registered. No caller of that wrapper appears in `GraalEngine.dll`. The 3D body calls the scene's ray cast (two points and a mask, walking objects whose mask matches) and returns. The decompile does not show the four arguments being turned into those two points. **[bin]**

`graal_setSendGraal3DScriptEvent` stores a callback of two strings, the event name and the argument text. The engine uses it, only while the 3D flag is set, for `getgani`, `getweapon`, `getclass`, a client-variable send, and a weapon `trigger`. The 3D body resolves the current connection's script object and passes both strings on. **[bin]**

## What an interior read rejects

`Interior::read` reads one value and, if it is not zero, logs an incompatible-file message and returns false. If the stream already reports an error, it returns false without that log. Later reads return false on the same stream error. The decompile does not show a version number in the log text. **[bin]**

`InteriorResource::read` reads one value and, if it is not 44, logs its own incompatible-file message and returns false. When a following flag byte is set it reads a PNG into a bitmap. That is the rejection and the one branch that is visible; the rest of the record is not described here. **[bin]**
