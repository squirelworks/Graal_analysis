# Archives in the 3D resource registry: 4.04r2, 5.12 and Linux 4.20r6 (T3D-012)

Date: 2026-11-25. Static read of the Windows 4.04r2 3D engine (with its 2D engine) and the unpacked 5.12 engine image, following the code that uses the archive extensions and `levels3d`. The lab run used Linux 4.20r6 (3D-equal to Windows 4.20r8, [T3D-004](3d-engines-5007-512-and-403-411-2026-11-25.md#t3d-004-linux-and-mac-against-their-windows-twins)), because the lab has no 5.12 3D route on our own server outside the shared Windows VM. Board row: [T3D-012](3d-capability-board.tsv). **[bin]** unless marked.

## What each build has

| | 4.04r2 | 5.12 |
| --- | --- | --- |
| Zip reader | yes, in the 3D engine | yes: minizip "unzip 1.01" linked in |
| Mounted as archives | `.zip`, `.gpake` | `.zip`, `.gpake`, `.wba` |
| Plain `.gpak` | refused: the registry returns early for a `.gpak` name before adding or mounting it | refused the same way |
| Encryption | read encrypted only if a key is stored for that file name, otherwise read as a plain zip; the key is set by the 2D engine through a hook | the same; 5.12 also has `.enc` for single encrypted files |
| When | automatically, whenever a file with an archive extension enters the registry | the same |
| Start-up scan | recursive over the data and user folders, skipping `pms`, `profiles`, `weblevels`, `scriptfiles`, `updatepackages`, `src`, `ignore` and `.code` files | recursive, skipping only `src`, `ignore` and `.code` files |
| Files that arrive later | the 2D "file updated" hook registers any file under the user folder at once (and reloads a loaded resource of that name), so an archive is mounted at once | the same entry point has five callers; the live route is the same design [inf] |
| Lookup | keyed by the lower-cased bare file name; each archive member is registered under its own name, so `foo.dts` is found in whichever archive or folder holds it [inf for folders inside the zip] | the same design [inf] |

**Where downloads are saved (2D rule, both builds):** under `levels3d/`, `.gpak` and `.gpake` go to `gpaks/`, `.dts` to `shapes/`, `.dsq` to `anis/`, `.dif` to `interior/`, and in 5.12 `.ft` to `trees/`. `.zip` has no folder of its own, so a downloaded zip goes to the default download folder, still under the user folder [inf]. No extension blacklist that would stop a `.zip` being saved was found.

## Answers

- **Both builds open `.zip` and `.gpake` archives and read shapes and textures from them**, mounted automatically and found by file name. 5.12 adds `.wba`.
- **Plain `.gpak` is not mounted by either build**, although the 2D side saves downloaded `.gpak` files to `levels3d/gpaks/`. No other route that mounts `.gpak` was found.
- **Folders:** archives anywhere under the data or user folder are mounted, apart from the skipped folders above; `levels3d/` is not required.
- **Server-sent files:** reachable on the static view. A downloaded `.zip` should be mounted without a restart; a `.gpak` is saved but ignored; a `.gpake` needs its key first, or it is read as a plain zip.

## Lab: Linux 4.20r6 (zip420, 2026-11-25)

**Static check first [bin]:** Linux 4.20r6 has the same archive support as 5.12. Its zip reader is minizip linked in. `.zip` and `.gpake` are mounted, `.gpak` returns at once and `.enc` is flagged as encrypted; there is no `.wba`. The start-up scan covers the client and user folders and skips only `src`, `ignore` and `.code` files. Received files go through the same registry entry.

**Run [lab]:** the native Linux 4.20r6 client against our own 3D lab server, loopback only, software GL, with no movement input.
- The payload was a renamed MIT octahedron `.dts`, whose material asks for a texture `green`; a renamed textured `.3ds` cube that uses `labtex`; and `labtex.png`.
- None of these names existed loose on the client or the server. The world ghosted a served reference cube plus two GameObjects naming the two shapes.

| Run | Client has | File requests in the 3D phase | On screen |
| --- | --- | --- | --- |
| zip420-0 (baseline) | nothing | both shapes, not found | reference cube only |
| zip420-a | `levels3d/test.zip` with both shapes and `labtex.png` | **none for the zip's members**; only `green` (not in the zip), not found | **both shapes draw**; the cube carries `labtex` from the zip |
| zip420-b | the same bytes as `levels3d/test.gpak` | both shapes, not found | reference cube only |
| zip420-c | the three files loose in `levels3d/` | **all three still asked for** (server: not sent), plus `green` | both shapes draw, the same picture as zip420-a |

- **A `.zip` in `levels3d` is mounted at start-up, and shapes and textures load from it** like loose files. A file the shape names that is not in the zip is still asked from the server.
- **A plain `.gpak` is ignored**, as the static read says.
- **Archive members are never checked with the server**, while loose files are still requested each time. So a newer copy on the server would not replace a zip member [inf].

**Not reached: a zip delivered mid-session.** This client did not fetch a `.zip` named as a GameObject shape (it fetches only shape-type files [inf]). It did not fetch one as an NPC image in the 2D start level, which a 3D session does not load. It did not fetch one listed in `basepackage.gupd`, whose files are not fetched. Mounting without a restart needs a server that pushes a file, and it stays untested; statically, a saved file goes through the same registry entry and is mounted at once.
