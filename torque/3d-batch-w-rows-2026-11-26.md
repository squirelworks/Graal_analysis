## T3D-079: what 4.20r8 Windows crashes on after a TerrainBlock arrives

Client: unpacked 4.20r8 (`G3D20126`). The console confirms GDI Generic, with only
`EXT_paletted_texture` enabled. One change per run:

| Run | World | Camera height above terrain | Result |
|---|---|---|---|
| t0 | no TerrainBlock | n/a | links, draws sky and objects |
| t1 | TerrainBlock with **zero chunks** | spawn default (low) | **crash** |
| t2 | t1 plus 256 streamed chunks | low | **crash** |
| t1 | heights.info refused | low | **crash** |
| t1 | spawn raised | 3000, 600, 300, 200 | **no crash**; white (untextured) terrain drawn |
| t1 | spawn lowered | 100, 30 | **crash** |
| control | 5.12 on t2, same guest and GL | low | terrain drawn, no crash |

- The crash text is "Access violation at address zero. Read of address zero" (a null call),
  right after the console line "Loading terrain from terrain chunks.". TCP stays up and the 3D
  link times out.
- **It is not the terrain data.** A TerrainBlock with no chunks, no heights.info and no texture
  crashes the same way, and full streamed chunks do not change it.
- **It is the near-terrain render path.** With square size 8 it crashes when the camera is 100
  units or less above the terrain and never from 200 units up, where 4.20r8 draws the terrain
  on the same GL.
- Together with the earlier runs (no crash on accelerated GL or on Mesa, T3D-117), the trigger is
  a GL entry point the near-terrain path calls without checking, which GDI Generic does not
  provide. 5.12 on the same GL is fine, so 5.12 either checks it or does not use it. **[lab]**
  **[inf]** for the "unchecked entry point" reading.
- **Mesa check, same guest:** with a 32-bit Mesa 12.0 `opengl32.dll` (llvmpipe) placed beside the
  4.20r8 client, the near-terrain world (camera 30 units above the TerrainBlock) runs clean: no
  access violation, white terrain drawn, link held for the full 90 s run. So the crash is
  GDI-Generic-only. The same run showed that 4.20r8's "stuck at login" under Mesa was the start
  form waiting for its password field and a Start click, not the renderer. **[lab]**

## T3D-125: do the typed GS2 functions behave as declared on live 5.12?

A `weapon3d` probe called each function with the declared argument types and with wrong ones,
then isolation runs for the crash below. Client: 5.12 Windows.

- **Declared types are checked for arity only.** Too few arguments logs
  "GraalScript: Not enough parameters for GameObject.<fn> (N needed, M given)" and returns the
  default. Wrong types are coerced with no message: a name string works as the object for
  `mountObject`; an int or a word works as a position for `getdropz`.
- `mountObject(object,int)` returns 1; `getMountedObjectCount`, `getMountedObject`, `isMounted`
  and `unmountObject` behave as typed. `mountObject(obj,"x")` = 0, `mountObject(NULL,0)` = 0,
  `mountObject(player,0)` (an object onto itself) = 1.
- `move3d("0 2 1",1,0)` moves the own object by that **relative** offset (0,0,1 to 0,2,2), but
  only when the world line is `movetype list`; with no movetype or `interpolate` it does nothing.
- `findimg(anything)` returns an unnamed object, never null.
- `getdropz` returned 0 and `checkCollision` / `checkCollisionByBox` returned null in a world
  with no terrain and no `.dif`.
- `player` reads back as an object named "ServerConnection" whose position is the own object's.
- **Crash:** `mountObject(player,0)` followed by `move3d` under `movetype list` ends the 5.12
  process (stack-check failure, then access violation), 3 runs out of 3. `move3d` after mounting a
  separate GameObject is fine. A server should not let a script self-mount the player.

## T3D-126: WorldEditor, TerrainEditor and EditManager opened live on 5.12

`weapon3d` probes create each editor and call its typed methods. File trace: a file-system
watcher over the whole system drive for the run (Procmon froze the 2 GB guest and was dropped).

- **All three are created** from a `weapon3d`.
- **WorldEditor** works on objects the script made itself: `getMode` is "move", `undoLimit` 40,
  `gridSize` "10,10,10". `selectObject`, `dropSelection`, `undo` and `redo` run, `isDirty` goes
  from 0 to 1, and `deleteSelection` removes the selected script-made GameObject. `player` cannot
  be selected.
- **TerrainEditor** lists 17 actions (`select` … `clearModified`), but `attachTerrain` fails for
  every name tried ("TerrainEditor::attach: failed to attach to object '…'"). The first brush call
  on the unattached editor silently stops the script. `findobject` is not available in
  `weapon3d` ("Function findobject not found"), so a script cannot name the server TerrainBlock.
- **EditManager** has no members.
- **Nothing was saved**: no `.mis`, `.ter` or `.cs` anywhere. The only writes were the usual
  logs, caches, `.code` files and downloads.
