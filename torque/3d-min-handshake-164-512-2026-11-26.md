# The minimum replica handshake — what a proto-24 client must send to link and be seen (T3D-164)

Date: 2026-11-26. Lab: a ~400-line synthetic Python client on the host loopback against
seihai-gserver main (5cd9c15), with a real 5.12 under Wine/Mesa in the same world as the
second client. Behaviour only; the synthetic client and its bit readers stay in the lab kit,
off every PR. **[lab]**

This answers T3D-164: the smallest set of packets a replica client must send to be accepted
by a compatible server and to appear to other real clients. It builds on the protocol-24
link shape from [the UDP session note](udp-session.md) and the class table in
[T3D-160](3d-class-table-160-512-2026-11-26.md), and confirms the client-authoritative
position model (no Torque moves on proto 24): a proto-24 player reports its own position in
the game section, not through the move stream.

## The accepted path (what the server requires)

A replica is accepted and delivered a control object after exactly this sequence. Each step
is necessary; the server stalls or errors if one is missing.

1. **TCP gen-5 login.** A zlib frame (u16 BE length + deflate) carrying login type 5: key,
   8-char token, account (GSTRING), password (GSTRING), platform tail. The server logs the
   account linked as player N. The server's ~2.3 KB gen-5 reply need not be decoded.
2. **UDP challenge.** Out-of-band on the TCP port + 1: client sends the challenge request,
   server returns the challenge plus a 16-byte digest.
3. **UDP connect request.** A bit-packed GameConnection request: class group 0,
   crc 0xffffffff, connect string "Graal3D", protocol 24/24, password, args `[account, ""]`,
   echoing the server's digest. The encoder reproduces a captured 5.12 request bit for bit
   (568 bits for its own account). The server replies with a 276-byte connect-accept =
   the 19-entry class table (10 object + 9 event ids) + protocol 24, and logs the link
   as protocol 24.
4. **First data packet.** The server sends nothing for ~8 s after accept; it waits on the
   client's first data packet (the MissionStartPhase1 gate). The packet must carry a real
   game section — the real 5.12's first-person first data packet (max rate 32 ms / 450 B,
   game section first-person flag 1, position 0). Zero-padding is rejected
   ("could not read client game section").
5. **Mission-start acks.** For each server data packet, the client sends a packet whose
   header acks the server's sequence (one ack-mask byte), both rate flags 0, its game
   section, and — when the server delivers the guaranteed `MissionStartPhase1` /
   `MissionStartPhase2` RemoteCommands — a guaranteed `RemoteCommandEvent` (class 5) whose
   single argument is the plain-text command name `MissionStartPhase1Ack` /
   `MissionStartPhase2Ack`. **A plain-text-named RemoteCommand (arg type 1) suffices for the
   acks — the client needs no NetString/tag table of its own.**

After Phase2Ack the server delivers the control object: its trace shows the five ghosts
created (Sun, Sky, the RED GameObject, the client's own `G3DPlayer_<acct>`, its Camera),
"finished the mission start", then "control object (ghost 3) delivered". No "could not read"
lines; the client's game section is accepted throughout.

**The client never has to decode the ghost section to be accepted and seen.** Every create
is skippable by its declared bit length.

## Moving, and being seen by a real client (R164d)

With a real 5.12 (pc:1) joined to the same world as the synthetic client (synth1 — separate
accounts so the TCP/UDP pairings can't cross):

- The server ghosts each client to the other: the real 5.12 gets
  "ghost 3 (GameObject G3DPlayer_synth1) created on the client"; the synthetic client gets
  `G3DPlayer_pc:1`.
- **To move,** after taking the control object the synthetic client sends, in each packet's
  game section, a GameObject update with only section 4 (transform: position, axis 0,0,1,
  angle 0). Sweeping x 2→10→2 at y 3 over 16 s produced 607 "control object" steps on the
  server (2.00, 2.06, … 3.00).
- **On the real 5.12's screen** a second red cube (the synthetic client's) sits beside its
  own and moves — next to it, mid-right, at the right edge, back — matching the 16-s sweep.
  So the real client follows the synthetic client's reported position.
- The server shows **0 moves received** for the proto-24 client, and the real 5.12 sends
  none either: position rides in the game section, not the Torque move stream.

No read errors on either side; both links held until quit with no drop.

## Reading the world back (R164e, beyond the row's question)

A ghost-section reader (lab-only) lets the synthetic client perceive what it is sent. The
ghost section reads as: `flag any`, `int4 index width`, then per entry
`flag 1, int<width> index, flag kill, [int12 class id, int14 bit length, payload]`, ending
`flag 0`. Every entry carries its class id and bit length, so unknown classes skip cleanly;
that held for every packet in the run with no truncation.

Decoded world (matches the world file — RED at 0 4 1, spawn 0 0 1, camera 0 −5 2 from spawn):

- ghost 2 GameObject "RED", shape `redcube.3ds`, at (0,4,1);
- ghost 3 GameObject "G3DPlayer_synth1", shape `redcube.3ds`, at (0,0,1), nickname "synth1",
  flags 4351 — its own avatar / control object;
- ghost 4 Camera "G3DCamera_synth1" at (0,−5,3);
- Sun and Sky received, bodies skipped by length (field layouts still undecoded).

## Verdict

The minimum viable proto-24 replica handshake is: gen-5 TCP login → UDP challenge → connect
request echoing the digest → a first data packet with a real first-person game section →
per-packet acks with plain-text `MissionStartPhase1Ack`/`Phase2Ack` RemoteCommandEvents.
That is the whole contract to be *accepted*: a ~400-line client takes the full path, links,
clears mission start and is handed a control object. To be *seen*, it then emits a GameObject
section-4 transform each packet; a real 5.12 ghosts it and tracks its position live. Decoding
the ghost section is not required to join — only to perceive — and it is uniformly
length-delimited, so a replica can skip every class it does not yet understand. Still
undecoded (all skippable by length): Sun/Sky/terrain/water/replicator field layouts and the
BigData "events" text.
