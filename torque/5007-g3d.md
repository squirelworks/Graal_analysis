# Graal3DEngine.dll 5.0.0.7

Date: 2026-11-07. Static read of the 3D DLL decompile. Nothing was run. The launcher beside it is file version `5.0.0.7` ([5007-launcher.md](5007-launcher.md#startup)). **[bin]**

`loadGraal3DEngine` stores one argument and parses the other as a command line: `-connect` plus the next word becomes the start-connect string, and `graal://` or `graal3://` is handed to `setGraalProtocolString`. It then calls a virtual on the engine object. `runGraal3DEngine` and `endGraal3DEngine` are single virtual calls. A separate routine, with no direct caller recovered in this decompile, registers this DLL's draw and 3D callbacks over the engine setters and then calls `graal_engineInitialize`. **[bin]**

## GameObject

`GameObject` is registered as a Torque class name. Its Graal property table is a `TProperties` whose class is `GameObject` and whose parent is `SceneObject`. `Camera`'s table is parented on `GameObject`. `TGameObjectAttr` is parented on `TGraalVar`. Code that walks a terrain cell dynamic-casts a `SceneObject` to `GameObject` and, on success, calls a virtual on it. **[bin]**

Each `GameObject` property is a `TGraalVarProperty`: a name, a type byte, and a getter and setter. The names cover appearance and movement (`alpha`, `collision`, `shape`, `shapebox`, `nickname`, `velocity`, `liquidtype`, `shadow`, `solid`, `showterrain`), mounts and nodes (`mountObject`, `unmountObject`, `getNodePosition`, `getMountedObject`), interiors (`isInInterior`, `getInteriorObject`), collision tests (`checkCollision`, `checkCollisionByBox`, `getdropz`) and show-images (`findimg`, `hideimg`). `Camera` adds `cameramode`, `followattachedobject`, `lookatposition`, `lookvector` and `eulerrotation`. Which byte means which Graal type was not read property by property. **[bin]**

`ShapeBase`, `PlayerData` and `GameBase` do not occur. There is no `.dso`. `SimObject` does occur in this DLL; it does not occur in `GraalEngine.dll` ([5007-engine.md](5007-engine.md#no-simobject-and-no-dso)). **[bin]**

## Mission phases

Login progress is a step number and an `onGraal3DLoginStep` event on the universe. Two download phases run, then the control object. **[bin]**

| What runs | Step passed to the event | What else |
|---|---|---|
| Logs the phase-1 ghost-download line | 2 | builds a packet named `MissionStartPhase1Ack` and posts it on the connection |
| Logs phase 2, mission lighting | 3 | raises the event only when the lighting call returns true |
| Logs `Mission lighting done` | 4 | posts `MissionStartPhase2Ack` the same way as phase 1 |
| Logs the initial-control-object line | 5 | then calls the step-6 routine |

Step 6 runs only when the step is already 5 and no file download is active. It looks up `GUIContainer`, casts it to `GuiControl`, and calls `GuiCanvas::setContentControl`. It looks up `GraalControl` and `GraalControl3D` and passes each to a virtual on that container, then raises `onGraal3DLoginStep` with step 6. **[bin]**

There is no datablock-download phase string. The word `datablock` is a key in an interior sub-object, below. **[bin]**

## Terrain chunks

`TerrainChunkEvent` is registered as a net class. The function that unpacks one packet was not recovered, and this decompile has no "sending terrain chunk" string, so the packet layout is not visible. **[bin]**

What a chunk load does to the files is visible. A path is built from the user folder, `levels3d`, `heights`, and the escaped server name. `heights.info` is loaded as a comma-separated list from that folder. If the file is not there, the same name is requested through `getLevelFile`, and an empty result stops. The list is then applied to the terrain object. **[bin]**

A single chunk, given two indices, builds a file name under that folder. If the file exists it is loaded, decompressed, and a checksum of the plain bytes is stored. Those bytes are wrapped in a stream and a reader consumes the stream into the terrain block. The field order inside that stream was not recovered. The matching save path compresses the stream and writes the same file. **[bin]**

## Protocol

The connect-request check reads 4 bytes from the stream and compares that value with 24. Equal returns success. Any other value stores the reason `CHR_PROTOCOL` and returns failure. A call in front of the read always returns true in this build, so it does not change the result. **[bin]**

The neighbouring virtual writes the game string `Graal3D` and then writes the value 24 twice, with the same 4-byte write. The check itself is only reached through that virtual table. No direct caller was recovered, so what a false return does after the reason is stored — a disconnect, a log line — is not visible in this decompile. **[bin]**

`CHR_INVALID` is a different check: two 4-byte reads must match a stored value and a table indexed by that value. It is not the protocol window. `CHR_PROTOCOL_LESS`, `CHR_GAME`, and a sentence about official clients only, do not occur in this DLL. **[bin]**

## Interiors

`Interior::read`, in both of its copies, reads 4 bytes and requires that value to be 0. Any other value logs `Interior::read: incompatible file` and returns failure. A non-zero stream status also returns failure. After that it reads counted groups: three floats, then four floats, then further indexed records, and one branch reads a PNG through `GBitmap::readPNG`. The meaning of each group was not recovered, so this is not a layout. **[bin]**

`InteriorResource::read` reads 4 bytes and requires 44. Any other value logs an incompatible-resource line and returns failure. A following flag byte, when set, reads a PNG. It then reads counts of detail levels. A detail level that fails logs `Unable to read detail level` and fails the resource. **[bin]**

A sub-object read takes a 4-byte key and accepts only 1. Any other key logs `Bad key in subObject stream!` and returns no object. On the objects that do load, the keys compared by name are `datablock`, `class`, `rotation` and `scale`. A key that matches none of those is left unchanged. **[bin]**
