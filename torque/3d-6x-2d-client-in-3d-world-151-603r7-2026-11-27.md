# A stock 6.x 2D client in a 3D world (T3D-151, 6.x leg of T3D-069)

Date: 2026-11-27. Lab: a headless Linux lab VM, against seihai-gserver
main `0aff085` (#230) with the lab 3D world and `graal3d_trace` on. Two real clients:

| side | client | how it ran |
|---|---|---|
| 2D | **stock** 6.03r7 Linux x64, native ELF, token `G3D0511C` (sha256 `ceeaefeb…9c50`) — the Quattro 2D engine, not our Frankenstein 6.037 | native, Xvfb |
| 3D | real 5.12 (sha256 `ece87e57…d018`) | Wine, Xvfb, software GL |

Each client sat in its own private network namespace (its own address) behind a
logging proxy on its side. Two runs of about six minutes each: **A** (5.12 joins
first) and **B** (6.x joins first), with keyboard walks and script-set looks on the
6.x and `g3dpos` moves and chat on the 5.12. Behaviour only; captures, logs and
screenshots stay in the lab kit. **[lab]**

## Results

| # | test | result |
|---|---|---|
| 1 | Coexistence and stability, both join orders | **PASS.** No drops, desyncs or crashes; no 6.x-specific server warnings or unknown packets. Server peak 5.3 % CPU, ~10 MB RSS. Each quit tore down cleanly; on the 6.x quit the 5.12 got its `G2DPlayer` deleted. |
| 2 | The 5.12's view of the 6.x player | **PASS.** A `G2DPlayer_pc:N` ghost appears, drawn as the world playershape (the cube), and moves with every 6.x walk and every script move. A 5.12 weapon3d reads its `.chat`; the 5.12 draws no chat or nick over it (as with 2.22/5.24r4). |
| 3 | The 6.x's view of the 3D player | **PASS.** Drawn as a default-look 2D sprite, present in `players[]`, follows each 3D move. 3D chat arrives in `players[].chat`, but the 6.03r7 draws no chat text and **no name tags at all** in this setup, not even its own. |
| 4 | 2D looks set by script on the 6.x | see the table below |
| 5 | Anything broken | **Nothing.** Level-NPC timeouts kept running on the 6.x the whole time a 3D player was in the level (the #211 level-leader fix holds for 6.x). |

### 2D looks from the 6.x

| prop | 6.x sends it? | reaches the 5.12? | 5.12 script reads it on `G2DPlayer`? | 5.12 draws it? |
|---|---|---|---|---|
| head | **yes** (5.24r4 did not) | yes, on its 2D (TCP) side only | no — empty | no |
| body | yes | yes, on its 2D side only | no — empty | no |
| colours | **yes** (5.24r4 did not) | yes, on its 2D side only | no — empty | no |
| nickname | **no** — `player.nick`, `player.nickname` and a later second write all stay local | — | — | no |
| chat | yes; the 6.x clears it itself after ~3 s | yes | yes (`.chat`) | no |

So a 6.03r7 sends more of its look than a 5.24r4 does (head and colours), and the
5.12 does receive them, but only on its TCP player stream: the server does not copy
head, body or colours into the 3D `G2DPlayer` object, so in 3D the 2D player is
always the world playershape. The nickname never leaves a 6.03r7 by script.

## Cross-view matrix (6.03r7 ↔ 5.12)

| property | 3D player → on the 6.x screen | 6.x player → on the 3D screen |
|---|---|---|
| presence | yes — default 2D sprite, in `players[]` | yes — `G2DPlayer` ghost, drawn as the world playershape |
| position | yes — follows `g3dpos` moves | yes — follows walks and script moves |
| chat | carried (`players[].chat`), not drawn | carried (script reads `.chat`), not drawn |
| nick | not drawn (the 6.x draws no name tags) | never sent by the 6.x |
| head/body/colours | nothing to set from 3D; default look | sent by the 6.x, reach the 5.12's 2D side, not in the `G2DPlayer`, not drawn |

## Smaller findings

- **Lobby ghost (run A).** The 6.x's brief first connection at the `Login` lobby
  appeared on the 5.12 for ~2 s as an extra `G2DPlayer`, then was deleted. Harmless,
  but the server could skip ghosting lobby-only sessions to 3D.
- **Trigger relay.** A client's script trigger messages are relayed to the other
  player in the level even though the server logs them as dropped: the 3D client's
  script traffic is visible to 2D clients in the level. Worth a server check.
- **Send window full (run B only).** The 5.12 hit "send window full" while downloading
  terrain; on the 5.12 side and unrelated to the 6.x.

## Open

- Showing a 2D player's look in 3D needs the server to add head, body and colours
  to the `G2DPlayer` object (the 5.12 already receives them on TCP), plus a 3D-side
  draw for them.
- A 6.x nickname needs a server-side path (NPC-server or login profile); the lab
  had no NPC-server, so it was not tried.
- The Windows 6.03r7 leg was not run (the Linux 6.03r7 is the same release).
