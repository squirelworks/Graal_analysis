# Particles: the Torque datablock system is gone from 5.12, replaced by a GS2 one (T3D-085)

Date: 2026-11-25. Static read of the registered console classes and class-name strings in the Linux 4.20r6 (5.12-class, protocol 24) and 4.04r2 (protocol 19) engines, plus the GS2 `-listscriptfunctions` dumps across the protocol-24 family. Linux 4.20r6 is 3D-equal to Windows 4.20r8 and class-equal to 5.00r7/5.12 ([T3D-004](3d-engines-5007-512-and-403-411-2026-11-25.md), [T3D-003](3d-engines-5007-512-and-403-411-2026-11-25.md)). Board row: [T3D-085](3d-capability-board.tsv).

## Answer

**No — the 5.12-class engine does not render the Torque `ParticleEmitterNode` + particle-datablock system. Those classes are dropped, not merely unused.** 4.04r2 registers the full set. 5.12 **replaced** it with its own GS2-scriptable particle system.

## Class evidence **[bin]**

Scanning each engine's registered console classes (the class-representative built at start-up) and its class-name strings:

| Class | 4.20r6 (5.12-class) | 4.04r2 |
| --- | --- | --- |
| `ParticleEmitterNode` | not registered, name string absent | registered |
| `ParticleEmitterNodeData` | absent | registered |
| `ParticleEmitterData` | absent | registered |
| `ParticleData` | absent | registered |
| `SimDataBlock` / `SimDataBlockEvent` | absent | registered |
| other datablock-era classes (Precipitation, Debris, Explosion, Splash, fxFoliageReplicator…) | absent | registered |

- 4.20r6 registers **28** console classes; 4.04r2 registers **117**. The whole datablock layer — every particle class among it — is in 4.04r2's set and absent from 4.20r6's, the same drop seen at the 4.10/4.11 switch ([T3D-003](3d-engines-5007-512-and-403-411-2026-11-25.md)).
- The GS2 `-listscriptfunctions` dumps agree across the protocol-24 family: 4.20r8, 5.00r7 and 5.12 all have **zero** `ParticleEmitterNode` / `ParticleData`, so 4.20r6 is a faithful stand-in for 5.12 here.

So the Torque particle classes are **unknown** to the 5.12-class engine. By the engine's own rule a ghost that names a class the client hasn't registered drops the connection, so such content is **rejected**, not quietly ignored.

## What 5.12 has instead **[bin]**

5.12 replaced the node/datablock system with a GS2 script-driven one. The binary and the GS2 dumps expose a Graal particle family to script:

- **`TParticleEmitter`** (a GS2 object): properties `particletypes`, `maxparticles`, `nrofparticles`, `emitautomatically`, `delaymin`/`delaymax`, `emissionoffset`, `attachposition`, `autorotation`, `clippingbox`, `emitatterrainheight`, `dropemitter`/`dropwateremitter` (sub-emitters), `currentparticlecount`/`emittedparticles` (read-only); methods `emit()`, `emitat(str)`, `advancetime(float)`, `addemitmodifier(...)`, `addlocalmodifier(...)`, `addglobalmodifier(...)`, `removemodifiers()`, `removeparticles()`.
- **`TParticle`** (angle, lifetime, speed, movementvector, sound…) and **`TParticleModifier`** (`addmod(...)`).
- An emitter is reached through a 3D drawable object's **`.emitter`** property (and a 2D `GuiShowImgCtrl.emitter` for the 2D side), plus a global `particleeffectsenabled` toggle.

So 5.12 **can** do particles, but through GS2 script on these objects, not through the `ParticleEmitterNode` datablock content 4.04r2 uses.

## Not driven live this session, and why

- **The lab gserver cannot send either path.** On the g3d420 route the server's datablock table is only `CameraData`/`PlayerData` (protocol 19) and its 3D class table is the 28-class protocol-24 set — no particle class. The world/scene format has only `sun`, `sky`, `object` (GameObject), `player`, `camera`, `tgeplayershape`, `weapon3d` — no particle/emitter line. So the server has no way to ghost a `ParticleEmitterNode` or a particle datablock to either client. The finding rests on the class tables, which are unambiguous.
- **The 5.12 script path was not driven live.** Reaching `TParticleEmitter` needs a 3D drawable object to read `.emitter` from, and earlier labs found the 5.12 client's own script can't `findobject` its own 3D object on this route ([T3D-018](3d-client-events-420r6-2026-11-25.md) context) — so a clientside GS2 weapon has nothing to attach an emitter to. A visible script emit would need server support for a reachable 3D drawable or the exact create/attach idiom, neither in hand; a run was not spent on a likely no-op. **[not run]**

## For a server

- **Do not ship `ParticleEmitterNode` / particle-datablock content to a 5.12-class client** — the classes are gone and an unknown-class ghost drops the link. That content belongs to 4.04r2-era (protocol 19) engines.
- A 5.12 particle effect is a **GS2 script** job on a `TParticleEmitter` reached via a drawable's `.emitter`, not server-ghosted datablock content.
