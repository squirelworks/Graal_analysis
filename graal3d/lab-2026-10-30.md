# Graal3D live lab (2026-10-30)

The real `GServer.exe` (MD5 `aab1a34a1f196d4f4fddf12112ccbf52`) and `Graal3D.exe` (MD5 `305c985a020cec6ab8d81ac95d447343`) from `graal3d.7z`, run under Wine 9.0 (32-bit prefix) with Xvfb in the cloud container. The results are folded into [protocol.md](protocol.md) and [formats.md](formats.md) with a **[cap]** tag.

## Setup

- **Server.** `GServer.exe` starts with an "Options / Start on port" dialog (default 14901). After OK it runs as a tray program with a small status window: "Server started at port 14901", "Server name: <host name>", "Current session count", and the buttons View players, Edit accounts, Update levels and Disconnect all RCs.
- **Levels.** The archive ships no `levels\` folder. The server needs `levels\startlevel.x`; copying the shipped `startlevel.x` there is enough.
- **Accounts.** The archive ships no `accounts.txt`, so every login fails until accounts exist. They can be made in Edit accounts (a tree with the folders Guest Accounts, Regular Accounts, Graalian Police, Trusted Admins, Administrators) or written by hand in the format in `formats.md`. The account editor holds: name, password, Load only, Blocked, Last IP, the four rights levels, and the player's level, view angle (default 270) and x/y/z, plus the look fields.
- **Traffic.** A small TCP proxy between client and server inflated every frame and logged each message both ways. UDP was recorded with tcpdump.
- **Clients.** The real client for login, props and the level transfer. Scripted clients (Python, the same codec) for everything in-world, because of the Wine limit below.

## The Wine limit

Graal3D draws with Direct3D **Retained Mode** (`d3drm.dll`). Wine's own `d3drm` is mostly stubs: frame `SetPosition`, `GetPosition` and `LookAt`, and mesh builder `GetFaces`, return without doing anything. As a result:

1. The first frame tick after the connect window crashes in the movement routine (access violation reading address 0), before the client flushes its login. Skipping that routine lets the login out.
2. Loading the level then stops at `GetFaces`, so the player frames are never made. Skipping the face list (it only feeds collision) lets the level load.
3. Loading the eight player meshes still fails, so other players are never created on screen. Positions read back from Wine are garbage, so moving would raise "Invalid floating point operation".

The lab therefore patched two places in the running process (not the file: the client checks its own exe and says "The Graal execution file is corrupted" if the file changes). With that, the real client connects, logs in, sends its look, nickname and UDP port, receives its props and the level, and saves the level file. It cannot show the world or other players, and it cannot be walked around.

**To go further,** the client needs Microsoft's own `d3drm.dll` (it is in `dxnt.cab` inside the DirectX February 2010 redistributable; winetricks has a `d3drm` verb for it). The container's network policy blocked that download. With the native DLL in the prefix, the same lab could capture movement, UDP position and chat between two real clients.

## What was confirmed

- Accept: `6` + `c(0)` before login. Login reject texts and the close.
- Login order, own props, the full props exchange, level name + text + leader, prop 50.
- The UDP relay rule: positions and chat go over TCP only when one side has no UDP port.
- Nickname guild-tag stripping and when the `3` echo is sent.
- Prop 14 from a client does not move the player.
- Saved props on the next login, and the saved nickname relayed first.
- Load-only accounts can log in many times; normal accounts give "The account is already in use."
- Disconnect: prop 51 to players, 56 to admins.
- Admin login (id 1): the account list (50), records (54), player joined/left (55/56), player props (59), message to all (8), kick (5).
- `accounts.txt`: exact layout, and a hand-written file is accepted.

A reference server written from the notes ([reference-server/](reference-server/)) gave the **same message stream** as the original for the scripted two-player session (login, moves with and without UDP, UDP hand-over, chat, level prop, leave, and a second login with saved props). The real client logged into it and received a byte-identical level file.

## Not confirmed

- UDP between two real clients, and how the client applies a peer's datagram (needs the native `d3drm.dll`).
- Admin commands 51–54, 59 (reply 57), 60 and 62 beyond the replies listed above.
- The "Disconnect all RCs" button and the player-list kick (packet 16) were not pressed.
